## What this repository is

`dsh-loom` is a DeepSeek Harness plugin that runs self-improving loops. A campaign is
one objective with a budget; a round is one iteration; each round dispatches subagent
attempts, verifies them mechanically, and promotes a patch only when the gate says the
gain is real. It self-optimises at four levels:

- **L0** the work itself (a patch that makes a spec pass),
- **L1** the work chain (which nodes run, with how many candidates),
- **L2** the loop policy (the chain/policy itself is a variable),
- **L3** the plugin's own code (the loop improving dsh-loom).

The loop is currently **OFF** (`rsi.enabled:false`, set by the human
2026-11-15 03:59). Nothing is dispatched until `rsi_control {action:"enable"}`.
~95 campaigns exist under `~/.dsh/loom/campaigns/`.

## The two remaining items

### A. L2 autonomy — the loop proposes a new loop, with evidence, and a human says yes once

What exists today:

- `proposeMutations(base, { fromVersion, max, decided, scopeEditable, rounds })` in
  `src/chain/mutate.js:140` proposes policy variants (`minimal-change`, `candidates+1`,
  `no-test-edits`, `state-your-uncertainty`, …), each tagged `status: fresh |
  already-decided | conflicts-with-scope`.
- `evidenceFor({ rounds, decided })` in `src/chain/mutate.js:115` builds the evidence
  bundle a human would need.
- `rsi_chain activate` refuses to switch to version > 1 without `confirm:true` and
  raises a `chain` checkpoint instead (the human gate, by design).
- `src/loop/decisions.js` persists `{kind, decision, base, candidate, at, report}` and
  the proposer reads it so a rejected idea is not re-proposed.

What is missing (this is the task):

1. **An automatic proposer.** Today `rsi_chain auto` must be called by a human. It
   should fire on its own trigger (plateau / repeated `stuck` / N rounds without a
   promotion) and write a proposal without being asked.
2. **Evidence attached to the card.** The checkpoint payload must carry: rounds
   measured on the current chain, spend, the predicted gain with its interval, the
   risk if it regresses, and the exact diff of the chain spec. A human should be able
   to approve from the card alone.
3. **One-click adopt.** `rsi_decide(approve)` on a `chain` checkpoint should activate
   the version (it currently only records the answer).
4. **Re-measure after adoption.** Once active, the loop must run L1 under the new
   chain and record whether the predicted gain materialised — otherwise L2 is a
   religion, not a measurement. Note 72 of 82 old campaigns had `policy: null`, i.e.
   L2 has never actually been in force in a live campaign. Prove it once.

### B. Continuous scoring + successive halving

What exists today:

- `scoreOf(attempt)` in `src/gate/score.js` returns `{ score, source }`, using a finite
  `killRate` when present (mutation kill rate), otherwise the binary pass/fail.
- `decidePromotion({ candidate, incumbent, config, evidence })` in `src/gate/gate.js:213`
  gates on complete/enoughTasks/baseline/gain/holdout and, since p3-gate, on
  `noiseSpread`.
- `planCandidates` / `hedgeDecision` in `src/loop/candidates.js` decide whether to buy
  a second candidate.

What is missing (this is the task):

1. **Continuous score in live rounds.** Most tasks still report no `killRate`, so the
   score collapses to 0/1 and the gate cannot see a 5 % improvement. Wire
   `research/mutants/`-style kill-rate measurement into the round for campaigns whose
   tasks are graded, and record `scoreSource` on every attempt.
2. **Successive halving.** Screen N candidates cheaply (half budget / fewer steps),
   keep the better half, then spend the full budget only on those. It must be a policy
   knob (`loopPolicy.halving`), not a rewrite: when it is off, behaviour must be
   byte-identical to today.
3. Prove it: a spec that fails today and a live campaign showing the money saved
   without losing the round's score.

## How to work here (this is the part that costs the most time to relearn)

- **Specs first, and they must be red.** Write `tests/selfNN/<name>.test.mjs`, run it,
  confirm it fails for the right reason (missing export, missing module), then let the
  loop turn it green. `scripts/test-all.mjs` deliberately excludes `tests/self*/` so a
  red spec cannot pollute the regression; when it goes green, add it to the standing
  list at the top of `scripts/test-all.mjs`.
- **Drive the work through RSI**, with `guard: '<node> scripts/test-all.mjs'` so
  autopilot cannot land anything that breaks the suite. Enable the loop first:
  `rsi_control {action:"enable"}`. Then `rsi_start({ id, workspace:'C:\\Projects\\RSI',
  template:'code-fix', auto:true, budgetUsd, budgetRounds, budgetMinutes, guard })`.
- **Node path** (Git Bash has no npm, and the default node is not on PATH):
  `C:/Users/Darkness/.dsh/dsh-runtimes/dsh-primary-runtime/dependencies/node/bin/node.exe`
- **Long commands**: `run_in_background: true`, then `job_output` with `wait: true`.
  `scripts/test-all.mjs` takes ~4 minutes.
- **Commits**: `git commit -m` with backticks or `$` gets eaten by the shell. Write the
  message to `.git/COMMIT_EDITMSG_loom` with python, then `git commit -F` it. Push with
  `git push origin HEAD`; the remote is public and needs no prompt.
- **The guard runs in a minimal environment (only `PATH`).** That is why
  `src/exec/git-bin.js` exists — twelve suites died with `spawnSync git ENOENT`
  otherwise. If a promotion is rolled back, reproduce it as autopilot does:
  `cmd.exe /c "set PATH=<node>;C:\Windows\System32;C:\Windows && node scripts\test-all.mjs"`.
- **Flaky rounds**: `scripts/guard-retry.mjs` re-runs a failed guard once and records
  `flaky … not counted`. Do not "fix" a flake by loosening the assertion.
- **Never call `rsi_dashboard` with ~95 campaigns** — it returns ~100 KB into your
  context. Use `rsi_status {id}` instead. Payload caps live in `src/core/limits.js`;
  never print a whole file or a whole JSON record.
- **Reloading the plugin**: `plugin_manager set_plugin {target:'include:dsh-loom',
  enabled:false}` then `true` (HMR does not re-apply). Check
  `~/.dsh/loom/apply.log` for `apply:done tools=NN`.
- **Panel route** is live at `http://127.0.0.1:<harness port>/dsh-loom/state` (find the
  port with `Get-NetTCPConnection`; two `DeepSeek Harness` listeners exist and only one
  is the GUI — the other is the LLM proxy and answers 404 for everything).
