# 对标记录（2026-11）

这份文件只做一件事：把 dsh-loom 自己的数字与**公开可查**的同类系统数字放在一起，
并明确标出哪些比较是同口径的、哪些不是。所有「对方」的数字都来自
`research/balance-2026-11.md` 里记录的来源；取不到一手数字的，这里就写「无一手数据」，
不拿记忆或二手转述充数。

## 2. 对方的数字（一手来源，口径不同）

| 系统 | 数字 | 口径 | 能否直接比 |
|---|---|---|---|
| Aider（gpt-5 high） | ≈220 秒/解决 | 单个 benchmark 题、单 agent、无 holdout 门 | 不能直接比：我们的「晋升」要求验证器 + 测试未被改 + 留出集全部通过 |
| SWE-agent / OpenHands | 无一手墙钟数字 | 只找到准确率与成本总量 | 不可比 |
| dream-rsi | 无公开效率数据 | 确定性循环 + 终止原因枚举 | 不可比（它不追求墙钟） |
| gear | 无公开效率数据；Windows 不支持 control-plane | 多容器编排 | 不可比 |

因此**唯一可以站得住的说法**是：我们的每次晋升比 Aider 单题解决慢 2–4 倍，
但我们的每次晋升包含的保证多得多（可复现补丁、测试未被修改、留出集未回归、可回放）。

## 3. 这份记录现在还不能证明什么

- 「比市面上都好」目前**没有**被证明。能证明的是：三角的每一腿都可测量、
  每一次花钱都有账、每个晋升都有证据、每一轮都能重放。
- 需要补齐才能做真比较：
  1. 同一批任务上跑 Aider（或 SWE-agent）作为基线，而不是拿公开摘要对比；
  2. 把留出集从墙钟里剥离（现在它算进回合墙钟，高估了我们的耗时）；
  3. 把 planMode off 的 651 秒与同任务的 planMode full 做**同任务**配对比较；
  4. 把「晋升」定义成公开 benchmark 的 pass@1，才能与上面的 220 秒对话。
