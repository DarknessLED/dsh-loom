## 落下来的东西

### `src/dispatch/stage-plan.js`（新）

`STAGES = ['triage','spec','implement','verify','review']`——这不是我挑的五个词，是 `HANDOFF.md` §4 用 8 任务 × 5 harness（`telemetry_iso.json`）量过的那五个阶段。`stageOf(task)` 只认任务显式声明且属于这五阶段的名字，`plan` 作为 `spec` 的别名保留（旧的三阶段词汇写在 `STAGE_ALIASES` 里，不让旧任务悄悄掉出计划）；未知名字**不猜**，退到 `implement`。

`ARMS` 记下每个阶段实测选中的 arm **以及判决它的那个数**：

| 阶段 | arm | 依据（HANDOFF §4） |
| --- | --- | --- |
| triage | `dsh` | 该阶段工具调用最少（8 任务共 56 次）——分诊就是一次模型调用 |
| spec | `cc` | 写之前读得最多（49 次 read vs 23–36），规格工作天然是读多的 |
| implement | `codex` | 编辑尝试最少（12 次 vs 13–24），有 model catalog 时一次原子 `apply_patch` |
| verify | `gcli` | 单命令执行最便宜（build 类 16.9s、6 次工具） |
| review | `agy` | 总耗时最短（170s vs 208–259s），且没看过实现者的推理 |

**这些 arm 是声明，不是执行**：本循环今天只有一个 harness（DSH 的 subagent dispatcher），不会去 spawn `cc`/`codex`/`gcli`/`agy`。所以每一轮把它写成 attempt 上的 `armTarget`，并且 `armWhy` 带着那句话——等哪天真有第二个 harness，账本里已经写着这轮该去哪、凭什么去。把「声明」记成「执行」是这套东西最容易犯的谎。

`dispatchPlan({task, config})` 在**开关关闭时返回 `null`**——不是空计划。这一条是「关时与今天逐字节一致」能成立的原因：没有下游代码能读到在这里凭空造出来的阶段，attempt 上也就没有 `stage`/`harness`/`armTarget` 三个键。

### 两个开关

注册在 `conversation.input.left`（composer 工具行的左侧，`conversation.input.permission` 就在这一行），一条注册、两个开关。形状是**药丸轨道 + 圆形旋钮**：关在左、开在右，状态先由位置读、再由颜色读；开启态的轨道用宿主自己声明的 `--dsw-alias-brand-primary`（这就是 DSH 的同款蓝，`#4D6BFE` 只是它没对外发布时的回落），关态是中性灰。不混色、不写第二份调色板——composer 不在 `loom-root` 里，`--loom-*` 不在作用域，所以这里读的是 `--dsw-*`。

- **RSI**：`POST /dsh-loom/state { action: 'disable' | 'enable' }`，走的是已有的 `runtime.setEnabled`。
- **Auto**：`POST /dsh-loom/state { action: 'dispatch', enabled }`，写 `settings.json` 并记审计。悬浮说明写清它 auto 什么：**先规划流程**（`triage → spec → implement → verify → review`），**再按阶段换最合适的 harness**，以及**当前只有 DSH 一个模型族与一个 harness，所以换的是框架与 preset、不换模型**；关着时与今天逐字节一致。

两条纪律写进了代码与规格：**点击后不乐观更新**（先 POST、再重新读 `/dsh-loom/state`，只有宿主回答了才改显示），以及**说明它要做什么**（`title` 不是只写「Auto」两个字）。悬浮文案里的阶段链与 arm 都来自 `/dsh-loom/state` 的 `dispatch.stages` 与 `dispatch.arms`，所以它念的是计划本身，不是一份写死在组件里的副本；最后一句明写「今天只有一个 harness，所以只登记该给谁、不真换」。无障碍上两个控件都是 `role="switch"` + `aria-checked`，旋钮是 `aria-hidden` 的装饰。

## 诚实的边界

- **本机只有一个模型族**，所以 Auto 能改的是框架与 `agentPreset`，改不了「谁回答」。开关的悬浮说明写「先规划流程」，不写「挑模型」，就是这个原因。跨模型自动调度要等有第二个模型族，而且那时也该由宿主的路由组来做，不该由插件二次发明。
- **`ssf` 的证据门没有接**。接它意味着插件要 spawn 一个外部 CLI，并假定 PATH 上有 node、`C:\Software\spec-superflow` 在位、变更目录位于 git 仓库里。这三条都是运行前提，不该由「打开一个开关」偷偷引入。今天落地的是它**量出来的路由表**，不是它的收据机制。
- **arm 是声明，不是执行**（见上）。账本里 `armTarget` 只说明「这一轮按实测该给谁」，不说明「谁跑了」。若哪天误把两者当一回事，那是这套东西最严重的误读。
- **开关没法在这个环境里截图**：当前宿主的 Web 端口没有在这个会话里监听（`curl 127.0.0.1:64553` 连不上），所以「我点了一下、它长这样」这句话我不能说。能说的是：bundle 通过 `tests/panel-client.test.mjs` 的 lazy-CJS 装载器挂载成功（12/12），`tests/self58/the-composer-has-two-pills.test.mjs` 钉住了注册的槽、两个开关的名字（RSI / Auto）、旋钮位移与宿主蓝色 token、悬浮说明的内容、两个 action 名，以及「只 require react」；`tests/ui/tones.test.mjs` 继续保证这抹蓝是 `var(--dsw-…)` 的回落而不是第二份调色板。
- **T3 不是依赖**，也刻意没做成依赖。

## 2026-11-28 深夜：Auto 的远侧接上了（arm 真的会跑）

上一节写了 Auto「只登记该给谁」。这一节把它接完，并说清哪一步是真的执行。

### 三个决定，各自有依据

1. **谁跑**：`ARM_PROVIDERS` 把 arm 对到 T3 Code 的 provider 实例。`cc → claudeAgent`、`codex → codex`、`agy → antigravity`；**`gcli` 没有 provider**，所以它不可路由——不拿最近的 provider 冲数，而是在 attempt 上记 `armNote.reason = "no T3 provider ships the gcli harness"` 然后退回 DSH 自己的子 agent。
2. **哪个模型**：`session.dispatch.models.default = "auto/deepseek-v4.1-flash"`，这是 magpie 的**路由组**（网关挑具体模型），语义上等于客户端里那个 Auto 模型选项。`perStage` 可以覆盖。T3 会拒绝 provider 没广告的模型，所以 `pickAdvertisedModel` 先只认广告过的名字，需要换时**必须**报 `adjusted: true` 并写明换成谁——换模型不能是静默的。
3. **跑不跑**：`session.dispatch.armExecution`（`off` 默认 / `execute`）。命名一个 arm 和运行它是两个权限：`off` 把 arm 写进 attempt，`execute` 才真交给 T3。`off` 是为了不让一次开关把这台机器的另一个账号额度花掉，而且**宿主不给我们计量**别的程序的 token（`armRan.billing = "unmetered"`，不是 0）。

### 传输的形状（已实机验证）

```
t3 thread start <cwd> - --provider <p> --model <m> --wait --json
```

brief 走 **stdin**（`-`），不进 argv：一个 attempt 的 brief 是几十 KB，Windows 命令行放不下，把它 quote 进 `.cmd` 只会让引号 bug 变成传输的一部分。`--json` 最后一行是 `{threadId, runId, status, reply, error}`；`parseT3Reply` 只认带 `status` 的那一行，失败也带对方的原话回来。

| provider | model | 结果 |
| --- | --- | --- |
| `claudeAgent` | `claude-haiku-5-5` | `status: "failed"`，`API Error: 402 insufficient_balance`（这条通道的钱包空了，不是传输坏了） |
| `codex` | `auto/deepseek-v4.1-flash` | `status: "completed"`，`reply: "LOOP-OK"` |

所以「T3 能不能替我们起别的 harness」这个问题已经有了答案：能，走 codex provider + magpie 路由组；`claudeAgent` 现在是额度问题。

上一节记了：`pill-route` 里一个任务是「把 impl.txt 改成 step:1」，却声明 `stage:"verify"`；一旦 verify 的 preset 填成审查者框架，就会拿审查者框架写代码。现在 `stageForNode(role, task)` 让**节点角色**说话：`recon → spec`，worker 才看任务声明（`taskKind` 优先，旧字段 `stage` 仍认），未知一律 `implement`。attempt 上多一个 `stageFrom`（`node:recon` / `taskKind` / `stage` / `default`），所以「这个阶段是任务声明的还是循环推的」以后可查。

- **T3 之外的两条路没接**：`harness.py` 的直接 spawn 契约（cc/codex/gcli/agy 各自的环境变量与 flag，HANDOFF §0 记着）仍然只在 Python 里，插件不调用它。T3 是当前唯一入口。
- **spec-superflow 的角色规划没接**：现在「分工」来自 `STAGES` + `NODE_STAGES` 两张静态表，ssf 的 `draft→executing→closing` 与证据门一个都没进来。要接的话第一步不是写代码，而是决定 `ssf workflow`（要求 git 仓库、`tasks.md` 形状、收据 head 等于当时 HEAD）与战役自己的账本谁是权威——两套账本并存会互相改写。
- **模型只到「路由组」这一层**：`perStage` 能填具体模型，但没有「按难度选模型」的逻辑；magpie 的 `smart-split` 组做的是这件事，所以 `default` 指向它就是让网关决定，我们这边不做难度判断。

## 2026-11-29 凌晨：角色选 harness，也选模型；ssf 的两份计划

这一节回答四件事：codex 的额度到底花在哪、两个开关为什么消失、Auto 怎么按角色同时选 harness 与模型、spec-superflow 的「动态计划」和实测表到底哪个好。

上一版文档说「那一轮花的是 Codex 账号额度」，**这是错的**。`~/.t3/caches/codex.json` 里 `auth.endpoint` 是 `http://127.0.0.1:3425`（magpie），models 全部是 magpie 的名字：

`codex` | `{"status":"unknown","endpoint":"http://127.0.0.1:3425"}` | `group/smart-split`、`auto/deepseek-v4.1-flash`、`opencode-go/hungerg-free`、`commandcode/gpt-6.2-sol` |

### 二、开关消失：`ctx.inject(['slots'])` 不再被回调

宿主现在给插件的客户端半区是 **dynamic Client half**：`ctx` 有 `slots`/`get`/`on`/`provide`/`effect`，React 通过 `ctx.React` 给，而不是 `require('react')`。`Slots.listSubTree` 显示 `conversation.input.left` 与 `sidebar.panellist` **都在、children 为空**——不是布局、不是挤掉，是一次注册都没发生。

`dsh-unlag` 1.17.10 的写法是**直接** `ctx.slots.inject(...)`，我们写的 `ctx.inject(['slots'], fn)` 不再被调用，于是两个开关与侧栏图标一起静默消失。修法：`apply` 先看 `ctx.slots.inject` 在不在，在就直接 `mount(ctx.slots)`，否则退回旧的 `ctx.inject(['slots'], ...)`。规格 `tests/self58/the-switches-mount-whichever-way-the-host-hands-slots.test.mjs` 两条路都钉住。**页面需要按刷新才看得到**：`~/.dsh/unlag-reload.log` 写着 reload 是手动的、没有 watcher。

### 三、角色：harness 与模型一起选

`src/dispatch/stage-plan.js` 现在每个角色返回两样东西：

| 角色 | harness | 实测 arm | 模型组 |
| --- | --- | --- | --- |
`triage` | triage | dsh | free |
`spec` | spec | cc | premium |
`implement` | implementation | codex | premium |
`verify` | verification | gcli | free |
`review` | review | agy | premium |

- 模型**先说意图，再由网关落地**：`triage/verify → free`（`opencode-go/hungerg-free`），`spec/implement/review → premium`（`auto/deepseek-v4.1-flash`）。这是 `models.perRole`，可用 `models.groups` 换掉两组的真名——所以 `gpt-6.2-sol`、`claude-opus-5-5` 上线时改一行，不用改角色表。
- 一个角色也能钉死某个 slug（`perStage` 或 `perRole` 写全名），此时 `modelGroup` 为 `null`：读者能分清「网关挑的」和「我们挑的」。
- 整机切换做 A/B：`models.plan: 'premium' | 'free' | null`，它压过所有角色偏好。
- 面板 `/dsh-loom/state` 新增 `planSource`、`modelGroups`、`roleModels`；Auto 的悬浮文案现在逐角色列出 `implement → premium`。

### 四、spec-superflow：读它自己的计划，再和实测表比

### 五、真机：`plan-ssf2` 一轮把它串起来了

工作区 `C:/Projects/RSI-live/plan-ssf2`（git base 提交后 `impl.txt` 是 `step: 0`，`check.mjs` 读它并打印 `KILLRATE=`），

### 这一节没有做到

- 动态计划只影响**主 attempt**的 stage/arm/model；recon 规划节点、screen、verifier 不读它。
- `ssf` 的角色表来自 `tasks.md` 的动词，不是 ssf 的私有计划模型；一个没写动词的步骤会被跳过而不是瞎猜。
- `planSource='ssf'` 时读的是 `state.workspace` 下的 `.spec-superflow.yaml`；改动目录不是工作区根时，它读不到（本次探针把工作区设成改动目录本身）。
- 免费组 `opencode-go/hungerg-free` 只用于**选名**，没有实测过它的分数；`models.plan='free'` 的 A/B 尚未跑。
