# 2026-11-21：候选定价器从没被调用过，而且它想砍的方向是错的

这一轮的起点是用户一句「继续下一轮优化」。没有指定方向，所以我先把整个账本量了一遍，再决定修什么。

账本：`~/.dsh/loom/campaigns/*/events.jsonl`，全历史 470 个 `round.finished` / 464 个 `round.started`，
attempt 支出 $10.2552，247 次晋升。

## 一、两个本该生效的东西，一个从没跑过，一个方向错

### 1. 时钟读不出来，所以定价器一次没被调用

`src/runtime/round.js` 的 `budgetLeftMsOf(state)` 写的是：

```js
const startedAt = Date.parse(state?.createdAt)
```

而 `src/core/reduce.js` 把 `createdAt` 写成 `ev.t` —— 账本里的时间戳是**数字毫秒**（例 `1794843743415`）。
`Date.parse(1794843743415)` 是 `NaN`，`Number.isFinite(NaN)` 是假，于是这个函数**恒返回 `null`**，
于是 `round.js` 里 `budgetLeftMs !== null` 那半个条件恒假，于是 `planCandidates`（把
`hedgeDecision` 包一层的那个函数）**从来没有被调用过**：

- 464 个 `round.started` 里带 `candidatePlan` 的是 **0 个**；
- 207 个 round 里确实留下了 `secondCandidate` 判定（59 条判「不买」），但那些判定**没有改变过任何一次
  候选数** —— `candidatesPlanned` 始终等于 chain 配置。也就是说，「我算过账，决定不买」这句话在账本上
  写了 59 遍，一分钱没省。

同一个 `Date.parse(数字)` 的写法还有两处，一起静默失效：

- `src/panel/api.js` 的 `ageMs` —— 面板「多久没动」恒为 `NaN`；
- `src/runtime/quality.js` 的 `roundMs` 时间戳回退 —— 只在没有 `durationMs` 时才用到，所以没暴露。

三处里唯一写对的是 `src/loop/migrate.js`：`typeof raw === 'number' ? raw : Date.parse(raw)`。

**修法**：新建 `src/core/clock.js`，导出 `toMs(value)`（数字 / 数字字符串 / ISO / Date → 毫秒，
其余 → `null`，**绝不返回 `NaN`**；数字字符串先按数字解析，否则 `Date.parse('2026')` 会当年份）与
`sinceMs(from, to)`。三处调用点全部换成它。

### 2. 定价器的量纲是混的，而且「不买」比「晚点买」糟

`src/runtime/candidates.js` 的 `admitSecondCandidate` 算的是

```js
ev = p * (1 - p) * roundMs - tailMs - marginMs
```

`roundMs` 和 `tailMs` 都是**时间**，但这个 EV 想回答的是「第二个候选值不值」——收益应该是
「多一次晋升机会」的价值（美元或分数），不是「整轮墙钟的毫秒数」。量纲混在一起，结论就不可信。

把时钟修好之后，我按正确口径重放了整个账本（`solved` 定义收紧为 `verifierOk === true && score === 1`，
之前的估算把 `score` 当解决是错的，killRate 任务里 0.6 不是解决）：

| 反事实 | 省下的钱 | 丢掉的晋升 | 代价 |
| --- | --- | --- | --- |
| 否决 → 只跑一个候选 | $1.6054（15.7%） | **17 次，$0.7954 已验证工作** | 少买 |
| 否决 → 改成 cascade（先跑第一个，不行再买） | $0.7912（7.7%） | **0 次** | 串行尾巴 +641 分钟（+27.2% 墙钟） |
| 全部 cascade | $2.1356（20.8%） | 0 次 | 463 个 round 全部串行 |
| 自动降级 `adaptiveCandidateMode`（要最近两轮每个 attempt 都恰好 1.0） | $0.0000 | 0 次 | 它在账本里只命中 23 个 round，**全是零成本 round** |

省 $0.79 换掉 $1.31 的已验证工作，这个方向是错的。而「改成 cascade」省得少一点、一次晋升不丢——因为
它问的问题不一样：**不是「第二个候选有没有用」，是「值不值得在知道第一个结果之前就付钱」**。

顺带说明两个数字的含义：380 个多候选 round 里，第一个 slot 已经 outright 解决的有 160 个，那些 round
花在兄弟上的钱是 $2.1356（占 attempt 支出 20.8%）；第二个候选的分数严格更高只有 62/380 = 16.3%，
持平 243（63.9%），更差 75（19.7%）。

**修法**：否决时不再把候选数减到 1，而是把 `candidateMode` 切成 `cascade`、`candidateModeSource` 记
`evidence`；只有「时钟不够跑第二次」（`no-tail-room`）才保持 `parallel` + 单候选，因为那种情况下
问题真的是「买不起」，不是「买早了」。

## 二、改了什么

| 文件 | 改动 |
| --- | --- |
| `src/core/clock.js`（新） | `toMs()` / `sinceMs()`，时间戳归一的唯一入口 |
| `src/runtime/round.js` | `budgetLeftMsOf` 用 `toMs`；`candidateMode` 改 `let` + `buyLate()`；`secondCandidateGate` 否决时 `buyLate()`；`planCandidates` 不再要求 `parallel`；应用处 `if (candidatePlan.mode === 'cascade') buyLate()` |
| `src/loop/candidates.js` | `planCandidates` 返回 `{count, buy, mode, reason}`，`count` 恒等于 `max`；否决 → `buy:false, mode:'cascade'`；`no-tail-room` → `mode:'parallel'` |
| `src/panel/api.js` | `ageOf(moment, now)`，`ageMs` 不再 `NaN` |
| `src/runtime/quality.js` | `roundMs` 回退走 `toMs` |

`src/runtime/candidates.js` 的 `admitSecondCandidate` 公式**没有改**。它仍然是时间量纲的东西，
只是现在它的「不买」被解释成「别在开跑前买」，而不是「别买」。真实的钱数要靠 cascade 那一栏
来衡量，而那一栏是正收益且不丢晋升。要把公式本身换成同量纲的版本，需要先把「一次晋升值多少」
写进账本——那是下一轮的事，这一轮不假装做完了。

## 四、诚实的话

- 这一轮修的是**「有代码、有规格、有文档，但从没在真实账本上生效过」**这一类东西。上面 59 条
  「拒绝买」和 0 条 `candidatePlan` 就是证据：规格只断言了源码里出现 `planCandidates(`，没有断言它
  真的被调用并改变了什么。新规格里有一条专门断言 `round.finished` 里出现 `candidatePlan`，就是为了
  堵住这个缺口。
- 反事实数字都是**账本重放**，不是重新跑战役。重放用的是每个 attempt 当时的 `score`/`costUsd`/
  `durationMs`，它不会改变「候选 2 会不会解决」这类没发生的事——它只回答「如果当时不并行买，账本会
  少花多少、少晋升几次」。这个口径写在上面，别把它读成「省下 $0.79」已经是现金。
- 「+641 分钟墙钟」是按每个 round 的 `durationMs` 相加估的，没有考虑并发上限（`session.maxConcurrent`）
  带来的排队，实际排队时间只会更长，不会更短。账本里 138 个设了墙钟上限的战役没有一个会因此撞线，
  但这是历史数据，不是保证。
