## 0. 结论先行

1. **我们的「图」没有边，也没有节点实例。** 链是一段扁平数组（`recon → map(attempts) → verify → gate`），`map`
   只按**数量**扇出（`over: 'candidates'`），`runPreMapNodes` 用数组下标当依赖——这是流水线加一个并行池，不是 DAG。
   `src/chain/spec.js` 的 `validateChainSpec` 只校验 id 唯一、`type` 合法、`verifier` 有 `cmd`、`map` 有 `of`：
   **没有 `needs`/`edges`，没有环检测，没有节点级超时或重试字段**。
2. **账本只记「完成」，不记「开始」。** `round.js` 只在 `:255`（复用）与 `:320`（真跑完）写 `node.finished`，没有
   `node.started`；一个 recon 节点随宿主消失时账本里除 `round.started` 什么都没有，`recovery.js` 只能写
   `round.finished{status:'interrupted'}`。「从崩溃处继续」不是没做，是**没有可依据的身份**。
3. **`node.finished` 已写进 JSONL，但 `reduce` 把它扔了。** `src/core/reduce.js` 的 `apply` switch 没有 `node.*`
   分支（`default: break`），面板、`rsi_status`、任何读 `state` 的规格都看不见规划段跑过什么。
4. **外部系统的共同点是「节点有实例身份 + 状态转换先落账 + 重启从最后一条事件处继续」，不是「并行」**：
   Temporal 的 Event History/Heartbeat、LangGraph 的 super-step checkpoint、Airflow 的 Task Instance 状态机、
   Dagster 的 partition 覆盖。**并行在四者里都是推导出来的，不是前提。**
5. 按（实测收益）/（风险）排序：**D1 → D4 → D2 → D3 → D5（先普查）→ D6（不排期）**；绝对收益最大的是 D5，但它唯一
   会改变候选独立性，所以先测量、后开工（§6 给验收口径）。

## 1. 今天这个循环测得到什么

`round.finished` 携带 `durationMs, planMs, attemptMs, verifierMs, verifierRuns, holdoutMs, holdoutRuns, tokens,
costUsd, candidateMode, candidatesPlanned, skippedCandidates, abortedCandidates`（外加 `status/score/promoted/
planTimedOut/holdoutId`）。账本是**每战役一个 append-only JSONL**；晋升门 = verifier 通过 + holdout 不回退 +
`testsClean` + 超过该任务历史最好分（`policy.minGain`）。可推导的事实只有三条：

| 事实 | 怎么来 | 实测 |
|---|---|---|
| 一轮墙钟 = `planMs + max(attemptMs) + gateMs` | `roundStats`（`round.js:486`），`gateMs` 靠差值反推 | loom-triangle 1912s/3 次晋升 = 637s/晋升；loom-tri2 3257s/2 = 1629s/晋升 |
| 规划段占比 | `planMs / durationMs` | 211–510s/轮，占 28–47%；tri2 全程 1242s = 38% |
| 第二候选是否值得 | 逐 attempt 的 `score` | r1a1 636s(1)/r1a2 815s(1)/r2a1 414s(0)/r2a2 559s(0)/r3a1 403s(1)/r3a2 422s(0)；a2 占候选时间 55%，3/3 轮零增益 |

**测不到的事实**全部与「节点」有关：规划段里哪个节点跑了多久、是复用还是真跑、崩在哪；哪个 attempt 被 watchdog
杀、idle 多久；holdout 抽中池里第几个分区；一次 `died` 丢了多少已写出的编辑。这四条正是 D1–D5 各补的一个字段。
`verifierRuns`/`holdoutRuns` 只在**真的 spawn 子进程**时自增（复用不计数），必须保持——把「节点身份」做成
「又多了几个 run 计数」是倒退。

另一个必须先说的成本事实：`Runtime.append` 每写一条事件都会 `reduce(view.ledger.all())` **全量重放**整个账本。
账本是 append-only 的，节点级事件会让每条新事件的代价随历史线性增长。所以**节拍型事实（心跳、进度）不能进账本**，
只能进可变的 lease 文件；账本只收「状态转换」。这条约束直接决定 D1/D2/D5 的事件形态与频率。

### 1.1 四种「子节点中途死亡」在账本里长什么样

这是本任务真正要回答的问题，因为它是「图调度」与「顺序循环」的分水岭：图系统能问「哪个节点死了、死在哪一步、
从哪里继续」，顺序循环只能问「这一轮要不要重来」。

| 死法 | 触发点 | 账本今天留下什么 | 缺什么 |
|---|---|---|---|
| 宿主崩溃 | 无 `catch`/`finally` 机会 | 残留 `leases/*.json` + `round.started`；下次启动写 `round.finished{status:'interrupted'}` | 哪个节点在跑、跑了多久、工作树在哪、`planMs`/`attemptMs`（interrupted 那行不带任何 triangle 字段，这一轮的账对不上） |
| watchdog 判停滞 | `>stallMs` 或过 deadline → `abort()` | `attempt.finished{abandoned:true}` + `attempt.abandoned{reason:'stalled'\|'deadline'}` | `idleMs`、`lastSeq`、`deadlineAt`；判决只活在内存 Map 里，取出即删 |
| 派发器超时 | `Promise.race` 到点 → `cancel()`+`dispose()` | `failureKind:'timeout'`、`timedOut:true` | 用的是哪个窗口、当时上限、超时前子会话推进到哪一步 |
| 子会话自己死掉 | `stopReason!=='completed'` 或空回复 | `failureKind:'died'`、`agentTail`≤12 行 | 死前已写出的编辑量——**这个其实有**：`makePatch`（`:935`）无条件执行、`patchBytes`（`:1047`）记账，连被放弃的 attempt 也有 `artifacts/r<n>a<i>.patch`；缺的是「允许用它续跑」的语义（D5） |

一句话：**四种死法里有三种，账本连「死的是哪个节点」都答不上来**；第四种答得上，却不许用它的产物。
D1（身份）、D2（判决入账）、D5（用 patch 当检查点）各自补其中一格。

## 2. 五个真实系统：顺序轮循环做不到的那件事

### 2.1 Temporal：Event History + Activity Heartbeat（读了 2026-11-08）

Workflow Execution 是 "a durable, reliable, and scalable function execution"，durability 被解释成 "the absence of
an imposed time limit"；恢复靠 Replay："During a Replay the Commands that are generated are checked against an
existing Event History"，失败后 "the Workflow Execution picks up where the last recorded event occurred in the
Event History"。可阻塞的 awaitable 只有 SDK 提供的那几种，其中一条是 "Starting a Timer: Progress can block until
the Timer fires"——**定时器是事件，不是进程里的 `setTimeout`**。（https://docs.temporal.io/workflow-execution）

Activity 侧补上「节点内」续跑：失败按 Retry Policy 重试，"Each attempt starts from the initial state, unless your
code uses a Heartbeat detail payload for checkpointing. The last recorded Heartbeat details are made available to
the Activity function on the next attempt, so your code can continue processing where it left off."；并建议把大块
功能拆成多个 Activity，因为这样才能 "have short timeouts, and be idempotent"。（https://docs.temporal.io/activities）

**顺序轮循环做不到的**：Temporal 从**最后一条事件**处继续，我们从 `round.started` 重来；它的重试策略写在定义里、
由运行时执行且可审计，我们的模型链只在 `context|tokens` 上换模型（`dispatch/session.js:classifyResult`），
`died`/`timeout` 直接放弃整个候选；它的 deadline 是事件，我们的 deadline 活在 `watchdog` 的内存 Map 里。

### 2.2 LangGraph：super-step 是 checkpoint 边界（读了 2026-11-08）

执行按 super-step 推进（Pregel 式消息传递），"After a super-step, nodes with no pending messages become inactive"。
checkpoint 只在 super-step 边界保存、**不在节点函数内部**，所以 "After an interrupt or retry, the affected node runs
again from the start of its function. Side effects before the pause run again."；原话 "A node is a checkpoint and retry
boundary"。恢复粒度看原语：`Task` 的已完成结果存档但父节点从头重放；`Subgraph` 从子图失败节点继续；`Graph node`
则 "Resume starts at that node. Earlier nodes do not re-run."。扇出用 `Send`，控制流用 `ConditionalEdge`/`Command`。
（https://docs.langchain.com/oss/python/langgraph/graph-api）

持久化侧：checkpointer 存 thread 的图状态快照（`thread_id` 定位）；`InMemorySaver` 重启即丢、checkpoint 需裁剪；
**子图有独立 namespace，"the parent graph may not see the changes immediately"**。
（https://docs.langchain.com/oss/python/langgraph/persistence）

**顺序轮循环做不到的**：我们的恢复粒度是整轮，LangGraph 的是节点；它明确要求节点重跑时**幂等**，
而我们连「这个节点重跑过一次」都没有记录。

### 2.3 Airflow：Task Instance 是一个有状态的对象（读了 2026-11-08）

Task 只声明依赖，真正跑的是 **Task Instance**——某个 task 在某次 Dag Run（因而某个数据区间）里的一次具体运行，
"they are also the representation of a Task that has _state_"。状态是封闭枚举：`none, scheduled, queued, running,
success, restarting, failed, skipped, upstream_failed, up_for_retry, up_for_reschedule, deferred, awaiting_input,
removed`。默认触发规则 "a Task will run when all of its upstream (parent) tasks have succeeded"，可改 Trigger Rule；
依赖**后置声明**在任务之外（`>>` / `set_upstream`），且 "Tasks don't pass information to each other by default, and
run entirely independently"（数据走 XCom）。（https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/tasks.html）

两个我们完全没有的状态：`up_for_retry`（失败但还有次数，会被重新调度）——我们的一次 `died` 就是终局；
`removed`（"The task has vanished from the Dag since the run started"）——链在平台期被变异，账本里没有
「这一轮用的节点集合变了」这条事实。

**顺序轮循环做不到的**：把「依赖」与「任务」分开声明。我们的依赖是 `preMapAgentNodes` 的数组下标，顺序即语义，
改顺序没有任何校验能挡住。

### 2.4 Dagster：物化是 (asset, partition) 的事实（读了 2026-11-08）

分区可按时间、静态类别、二维、动态类别或自定义日历定义；"When you materialize a partitioned asset, you choose which
partitions to materialize and Dagster will launch a run for each partition"，成功物化的分区在分区条上变绿。二维用
`MultiPartitionsDefinition({"date":…,"region":…})`，key 形如 `2024-01-01|us`，一次调度可为每个 region 各发一个
`RunRequest`。（https://dagster.io/docs/guides/build/partitions-and-backfills/partitioning-assets）

**顺序轮循环做不到的**：说清「哪些分区已被物化」。我们的 holdout 是
`holdoutPick = heldOut[priorRounds.size % heldOut.length]`——用**轮数**对**当前池长**取模。池子一旦增删任务
（`evalset.registered` 可在任何时刻发生），同一个 index 就静默换人，而账本里没有任何事件记录「决策当时的池子」。

### 2.5 学术侧：关键路径决定下界（读了 2026-11-08，摘要级，不作主论据）

`arXiv:1905.05119` 摘要直说 "each task is represented as a directed acyclic graph (DAG)"（http://arxiv.org/abs/1905.05119v1）；
`arXiv:1712.03209` 把「同一工作量在不同核上效率不同」作为前提（http://arxiv.org/abs/1712.03209v1）。只取两条结论：
**关键路径决定下界**——并行只压缩非关键路径时墙钟不动；我们的关键路径是 `plan → 最快的候选 → gate`，第二候选
（55% 候选时间、3/3 轮零增益）从来不在关键路径上；**资源异构**——候选与规划抢同一个 `attemptTimeoutMs` 窗口（C6/C9 已处理）。

## 3. dream-rsi 与 agent-teams：树还是图，子节点死了怎么办

### 3.1 dream-rsi：单 agent 的顺序树，死亡是一种**枚举事实**

`research/open-dream-rsi/`（读于 2026-11-08；上游 https://github.com/patrykorwat/open-dream-rsi）。README 的
Positioning 把谱系列成 Self-Refine/Reflexion/ExpeL/Agent Workflow Memory/ACE，差异点是 "None of these promote
candidates through counterfactual replay over an evolving recorded world — that promotion gate is this library's
structural difference"。四个平面：Learning（dreamer + replay gate）、artifact 状态（`ArtifactLifecycleManager`）、
转换历史（append-only `artifacts/events.jsonl`）、不可变证据（Discovery Trees）。第一条硬规则最值得抄：
**先追加不可变事件、再暴露新状态**；物化视图必须等于 `rebuild_artifact_state(events)`；审计事件不是 artifact。

`core/tree.py` 的 `TerminationReason` 是封闭枚举：COMPLETED / POLICY_STOP / TOOL_FAILURE / BUDGET_GATE /
SENTINEL_BLOCK / UNKNOWN，注释说它存在的理由："Replay must be able to tell 'the decision-maker chose to stop' from
'the runtime removed the option' — they mean opposite things for a counterfactual rollout."；`TreeNode` 还有
`thought`（一句计划，把分支选择从纯分数变成语义）。

**它是树不是图**：边只有 parent→child，没有跨枝 join；子节点死亡 = 写一个 `termination_reason` 后归档，**没有
「续跑」**，也不需要——单 agent 的下一步本来就从树上重新选。可迁移的是**死因分类学**（不是拓扑）：我们的
`failureKind` 加 `abandoned/reason` 已经更细，但**丢了「是我们杀了它还是它自己停了」这一维**（D2）。

### 3.2 agent-teams：任务图与委派谱系是**两套**结构

`C:\Users\Darkness\.dsh\profiles\desktop\node_modules\@nanmicoder\dsh-agent-teams`（读于 2026-11-08）。
`lib/types/event-types.d.ts`：`task-created` 带 `dependencies: readonly string[]`——**真 DAG，边显式存**；
`task-updated` 带 `attempt`/`attemptId`/`verdict`/`round`；`task-amended` 只允许 captain 改契约且**必须带
`reason`**；`team-halted` 记 `cancelledTasks`。

`lib/types/scheduler.d.ts` 的注释几乎是一份「子节点死亡处理」说明书：成员空闲但仍持有 open attempt 时被 **parked**，
"only an explicit captain reassignment may rotate that capability"；"Automatic retry is reserved for cold recovery,
when this process has not observed the durable owner settle its open attempt."；`DispatchTicket` 带
`attempt/attemptId/previousAssignee/recoveredOwned/previousAttemptId/dependencyOutputs`。依赖产物由
`collectCompletedDependencyOutputs` 收集：递归取 `status=completed` 的祖先、**拓扑序**，且 "Cycles stop that branch
only"（有环只废那一支，不炸整张图），单条上限 2000 字符、合计 12000。

而**委派身份不是任务图**：`lib/types/lineage.d.ts` 用会话谱系（`header.parentSession`，深度上限 32）判定谁是谁的
成员，注释里的教训（#176）："若沿 parent 链解析，captain 在自己 fork 里就不再匹配它领导的团队"。

**两条可直接搬的结论**：① **图管工作，谱系管所有权**——我们两样都没有：没有边，也没有「哪个子会话是哪个
attempt 的合法持有者」（`attempt.finished.sessionId` 存在，但没与「这次 attempt 是否已被回收」关联）。
② **自动重试只给冷恢复，不给热失败**——活着但没进展的成员不该被自动轮换；只有「本进程没看见持有者结算」才重试。
我们恰好相反：热失败（`died`）不重试，冷恢复（host 重启）直接把整轮记为 `interrupted`。

### 3.3 合起来看我们的位置

| | 节点实例 | 边 | 节点重试 | 冷恢复粒度 | 死亡分类 |
|---|---|---|---|---|---|
| Temporal | Activity Execution + attempt | Workflow 代码里的顺序 | Retry Policy（心跳可续跑） | 最后一条事件 | 失败类型 + retry 状态 |
| LangGraph | node × super-step | `add_edge` / `Send` | 节点整函数重跑（要求幂等） | 节点 | interrupt vs 异常 |
| Airflow | Task Instance | 上游/下游声明 | `up_for_retry` | 任务实例 | 14 态封闭枚举 |
| Dagster | (asset, partition) | asset 依赖 | 运行级重试 | 分区 | 物化成功/失败 |
| agent-teams | task × attempt | `dependencies[]` | 仅冷恢复 | 任务（ticket） | verdict + recoveredOwned |
| **dsh-loom** | **无**（只有 round/attempt） | **无**（数组下标） | **无**（除模型链） | **整轮** | `failureKind` 有，kill 原因只在内存 |

### 3.4 树、图、谱系：我们该抄哪一个

树我们已经有（`attempts[]` 就是一个 round 一个根），缺的是**边两端的身份**与**所有权**：没有 `nodeId`，边无处可挂；
只有不可校验的 `attempt.finished.sessionId`，续跑时无法证明「它确实是那个 attempt 的持有者」。
所以顺序必须是 **身份 → 判决 → 谱系/续跑 → 边**；反过来先建边，会得到没有节点可挂的图。这也是 D6 排最后的原因。

## 4. 提案（按 实测收益 / 风险 排序）

排序口径：收益 = 「每轮可省的墙钟」+「账本可回答的问题数」；风险 = 「改变派发语义 / 让回放不确定 / 让账本变贵」。
所有规格写在**新目录** `tests/dag1/`（与已落地的 70 套件不抢文件名，由 `scripts/test-all.mjs` 自动枚举），
遵守 26c28e4 的规矩：**先让规格红，再改实现**。

### D1 节点实例身份：`node.started` + `state.nodes`　【收益/风险最高｜风险≈0】

**可观测变化**
- 新事件 `node.started{round, nodeId, role, attempt, base, worktree, branch, deadlineMs, chainVersion}`，在
  `runPreMapNodes` **派发之前**写一次（每个节点一次，`attempt` 从 1 起）。
- `node.finished` 增 `attempt`、`deadlineMs`（`cached` 沿用现有 `reused`，语义不变）。
- `reduce` 新增 `state.nodes`，键 `${round}:${nodeId}:${attempt}`，值 `{status:'running'|'ok'|'failed'|'reused'|'lost',
  durationMs, planBasis, base, sessionId}`；`round.finished` 落地时仍在 `running` 的节点折成 `lost`——**只投影，不伪造成功**。
- `rsi_status` 的 round 行加 `plan: recon ok 414s` / `plan: recon lost`；panel 读同一份 `state`。

**钉住它的规格**：`tests/dag1/node-identity.mjs`
1. 夹具：`round.started` → `node.started{nodeId:'recon',attempt:1}` → **没有** finished → `round.finished{status:'interrupted'}`，
   断言 `reduce(events).nodes['1:recon:1'].status === 'lost'`。**现在必红**：`src/core/reduce.js` 的 `apply` 没有
   `node.*` 分支（`default: break`），`state.nodes` 不存在。
2. 顺序断言：同 `(round,nodeId,attempt)` 的 `node.started` 必须早于 `node.finished`；旧账本（只有 finished）仍能 reduce。
3. 幂等断言：重复的 `node.finished` 不改变投影（append-only 允许重复，投影必须折叠）。

**当前阻止它的**：`reduce.js` 无 node 分支；`round.js` 只在 `:255`/`:320` 写 finished，崩溃即零记录；
`docs/contracts.md` §5 的事件序列没有列 `node.*`，所以任何「照契约写」的规格都会认为这些事件非法（契约要先改）。

### D2 截止期与中止入账：让「谁杀了它」可回放　【收益中｜风险≈0】

**可观测变化**
- 新事件 `attempt.deadline{id, round, deadlineAt, timeoutMs, source:'config'|'lease'}`，在 `dispatcher.run` 之前写；
  `source` 只记**当时用的哪一种**窗口，本文不据此改窗口（收紧窗口是 C9）。
- `attempt.abandoned` 增 `{deadlineAt, idleMs, lastSeq, timeoutMs}`（现在只有 `{id, round, reason}`）。
- `recovery.js` 的 `round.finished{status:'interrupted'}` 增 `lostNodes:[nodeId]`、`leaseReason`，使「宿主重启」与
  「watchdog 判停滞」在回放里可区分。
- `round.finished.abortedCandidates` 改为由 `attempt.abandoned` 计数派生（现在由 `attempts.filter(abandoned)` 得到，
  被重启吞掉的那一轮根本不计入）。

**钉住它的规格**：`tests/dag1/deadline-replay.mjs`
1. 任一条 `attempt.abandoned{reason:'stalled'}` 之前 3 条事件内必须有 `attempt.deadline`，否则失败。
2. 构造「deadline 已过 + 无 abandoned + 有 running lease」的账本，断言 `planRecovery(...)` 把它归入 `staleLeases`。
   **现在必红**：`lease.js:18` 的 `writeLease` 记录 `{attemptId, round, sessionId, startedAt, deadline, lastSeq:null,
   lastAdvanceAt, state, reason}`，`lastSeq` 只在创建时写 `null`，之后没有周期性更新 → 冷恢复分不清「刚启动」与「卡了 8 分钟」。
3. 断言 `round.finished.abortedCandidates === count(attempt.abandoned 且同 round)`。

**当前阻止它的**：`watchdog.js` 的判决只活在内存 `Map`（`stallReason()` 取出即删）；`round.js` 虽把 `reason` 写进
`attempt.abandoned`，但**不带任何可核对的量**；`recovery.js` 只写 `round.finished{status:'interrupted',reason:'host-restart'}`。

### D3 节点级重试：只对传输失败、只按规格给次数　【收益中｜风险中（花钱）】

**可观测变化**
- 新事件 `node.retry{round, nodeId, attempt, retryIndex, max, reason:'died'|'timeout', previousSessionId, spentUsd}`。
- `round.finished` 增 `planRetries`（本轮因重试多花的尝试数，与 `planMs` 一起看成本）。
- 触发条件封闭：`failureKind ∈ {died,timeout}` 且节点非复用、且预算预检仍通过；`context|tokens` 走已有的
  「缩 brief 重发」（`retried:'smaller-brief'`），不产生 `node.retry`；任何 `verifierOk:false` 永不重试。

**钉住它的规格**：`tests/dag1/node-retry.mjs`
1. 假 dispatcher：第一次 `failureKind:'died'`，第二次 `ok`。断言晋升账本里恰有一个 `node.retry{retryIndex:1,max:1}`，
   且 `node.finished.attempt===2`。
2. 断言 `failureKind:'context'` 不产生 `node.retry`（回归：不能把已有路径重复计费）。
3. 断言 verifier 失败（`verifierOk:false`）的节点**没有** `node.retry`。
4. 断言预算预检拒绝（`round.finished.status==='budget'`）时不发生任何重试。
**现在必红**：`runPreMapNodes`（`round.js:200`）对每个节点只有一次 try，失败写 `ok:false` 后继续，
「计划段挂了」与「计划段跑出空结果」在账本里长得一模一样。

**当前阻止它的**：`validateChainSpec` 没有 `retries` 字段；`dispatcher.run` 的重试只沿模型链、且只在 `context|tokens`
上换模型；`tests/` 里没有任何规格要求「节点失败后重来一次」。

### D4 分区化的 holdout：把「抽中了谁」变成事实　【收益中高（审计）｜风险低】

**可观测变化**
- 新事件 `holdout.started{round, id, index, pool:[taskIds], poolSha, taskId}`（跑验证器之前）、
  `holdout.finished{round, id, verdict:'pass'|'fail', ms, exitCode}`；`round.finished` 增 `holdoutIndex`（保留 `holdoutId`）。
- 新事件 `holdout.skipped{round, reason:'no-pool'|'no-verifier'|'candidate-not-verified'}`，取代现在把 `'skipped'`
  塞进 `checks.holdout` 的做法——「没池子」与「候选没过基线」是两件事。
- `reduce` 出 `state.holdout = {pool, covered:[index…], lastIndex, sha}`，面板可画覆盖条（Dagster 的分区条）。

**钉住它的规格**：`tests/dag1/holdout-partition.mjs`
1. 三轮三 holdout 的账本 → `covered` 必须是 `[0,1,2]` 且无重复；第四轮回到 `0` 时必须有 `holdout.started.index===0`。
2. 在第 2 与第 3 轮之间 `evalset.registered` 新增一个 holdout 任务 → 断言第 3 轮的 `holdout.started.taskId`
   **与没有新增时相同**。**现在必红**：`holdoutPick` 用轮数与**当前**池长，池子变了就静默换人，账本无法发现。
3. 断言 `checks.holdout==='skipped'` 的场景必有一条 `holdout.skipped` 且 reason 非空。

**当前阻止它的**：取模算术代替了分区集；`reduce` 只存 `holdoutId/holdoutMs/holdoutRuns` 三个标量；
`gate.evaluated.checks.holdout` 用 `false` 表示失败、`'skipped'` 表示不做，两者共享同一字段。
（与 40718ef 的「holdout 轮转」规格不重复：那条钉**轮转顺序**，这条钉**决策当时的池子与覆盖集**。）

### D5 以 patch 为检查点：从死亡处继续（而不是从零重来）　【绝对收益最大｜风险最高｜**先测量再建**】

**为什么不是「保留工作树」**：保留工作树要 lease 扩字段 + TTL 清理，工作树会越堆越多，而删除发生在 `finally`
（除非 `keepWorktrees`）——恢复路径与清理路径互相打架。更便宜的机制已经在账本里：`makePatch`（`:935`）对
**包括被放弃的** attempt 都会执行，`patchBytes` 在 `:1047` 记账，patch 落在 `artifacts/r<n>a<i>.patch`。
**patch 就是天然的、不可变的检查点**，而且已经在审计链里。

**两种机制，默认 M2**：**M1 同树续跑**——保留工作树（`attempt.kept{id,round,worktree,branch,base,patchBytes,reason,
expiresAt}`），用 `sendMessage` 到旧 `sessionId` 继续（DSH 对 idle 目标起新回合、对不在场目标 cold-resume），代价是
TTL/磁盘/lease 须扩 `worktree`+`base`；**M2 以 patch 为检查点**（默认）——新树 `git apply` 旧 patch，新子会话的 brief
带上「你上一次已产出这个 diff，从这里继续」，代价是一次重复上下文、零 TTL，正对应 Temporal 的 "Each attempt starts
from the initial state, unless your code uses a Heartbeat detail payload for checkpointing."

**可观测变化（M2）**
- 新事件 `attempt.resumed{id, round, fromId, patch, patchBytes, base, freshSession:true, resumed:true|false, reason}`。
- `attempt.finished` 增 `resumedFrom`：让 evidence 里「续跑得到的分」与「干净起跑的分」可分，**晋升门不看这个字段**
  （verifier 仍是唯一裁判，节点成功≠artifact 更好）。
- `round.finished` 增 `resumedCandidates`（它不是 `candidatesPlanned` 的子集，两者必须能相加对账）。

**先决测量（spec 0，只读）**：`tests/dag1/death-census.mjs`——在写任何实现之前，扫所有战役的 `events.jsonl`，
输出 `failureKind × (patchBytes>0) × 是否存在 patch 文件` 的普查表；断言 (a) 只读，不写任何文件（mtime 快照），
(b) 输出**当前**分布。**门槛**：只有「`died|timeout` 且 `patchBytes>0`」占失败 attempt ≥20% 时才开工 M2，否则作废。
这是唯一一条把「测量」写成前置规格的提案，因为它省下的时间完全取决于死亡率，而死亡率目前未被统计。

**钉住它的规格（M2）**：`tests/dag1/resume-from-patch.mjs`
1. 夹具：a1 `failureKind:'died'`、`patchBytes>0`、`base=B` → 下一轮同 task 产生 `attempt.resumed{resumed:true}`；
   断言新工作树 `git apply --check` 该 patch 成功（**现在必红**：没有任何代码读 `attempt.finished.patch` 去续跑）。
2. `base` 变了（新 headCommit）→ `resumed:false`，且**不得** apply 旧 patch（宁可干净重来）。
3. 只允许 a1：`a2` 永不续跑（破坏候选独立；Large Language Monkeys 的 coverage 前提，见 `chain-2026-11.md` §2）。
4. 续跑 attempt 的 `score` 进 `attempts[]`，但 `candidatesPlanned` 不变；`gate.evaluated` 字段与干净 attempt 完全同形。
5. 同一 `fromId` 只能被续跑一次（幂等），第二次写 `attempt.resumed{resumed:false, reason:'already-resumed'}`。

**当前阻止它的**：`dispatcher` 是「一次 activation = 一个全新子会话」，超时路径直接 `dispose()`（`session.js` 的
`#one`）；`startActivation` 的 `childId?` 与 `sendMessage` 的 cold-resume 提供**宿主能力**，但 `round.js` 从未使用；
`attempt.finished.patch` 只被 gate（`hasPatch`）与报告消费；lease 无 `worktree`/`base`；没有字段区分续跑分与独立分。

**为什么风险最高**：它把「同一份编辑」带进下一次尝试，直接威胁候选独立性。所以必须默认关、只对 a1、只在未计分时，
且**排在 D1/D2/D4 之后**——先让人看清发生了什么，再让机器少花一次钱。

### D6 边与拓扑校验：今天收益为 0，所以排最后　【收益 0（单节点）｜风险低但无回报】

**可观测变化**（只在真的出现第二个独立节点时才值钱）：`chain.proposed` 的 spec 允许 `nodes[].needs: string[]` 并记录
`edges`/`topoOrder`/`cycles`；`node.started` 增 `deps:[{id,status}]`，依赖未满足时写 `node.skipped{nodeId, blockedBy}`。

**钉住它的规格**：`tests/dag1/edges.mjs`：① 有环 spec 被 `validateChainSpec` 拒绝（reason `'cycle'`）且**不产生**
`chain.proposed`；② `topoOrder` 与数组顺序无关（nodes 倒序，`topoOrder` 不变）；③ 每个 dep 必须 `ok`，否则该节点不得启动。

**当前阻止它的**：`src/chain/spec.js` 无 `needs`/无环检测；`runPreMapNodes` 的依赖是数组下标；`src/chain/mutate.js`
只能改 `candidates` 数与提示词，**改不了图的形状**——因为图没有形状可改。

**为什么排最后**：§4 已禁「为并行而并行」；今天链上只有一个 `recon` 节点，加边不会省一秒。**只有 D1 量出「第二个
节点真的独立」，D6 才有资格被排期。**

## 5. 不该建什么

1. **不要建通用 DAG 执行器（worker pool 跑链上节点）**。今天没有可并行的节点，也没有边；建出来只能服务一个只有一行的数组，代价是引入新调度状态机与新失败模式。等 D1 量出「第二个独立节点」再谈。
2. **不要把心跳/进度写进账本，也不要用 `setTimeout` 当定时器**。`Runtime.append` 每条事件全量 `reduce` 一次，
   高频事件会让账本变成二次成本；节拍信息进 `leases/*.json`（可变、不审计），账本只收状态转换。Temporal 的 Timer
   是事件，所以我们的 deadline 也必须先是事件（D2），再谈「按 p90 收紧」——进程内定时器重启后不存在，而账本必须能
   回放「它当时几点该被杀」。这条不是洁癖：它决定 D1/D2/D5 的事件频率。
3. **不要为「并行」把 `candidates` 提到 4，或把 `maxConcurrent` 提到 2 以上**。实测第二候选占 55% 候选时间、
   3/3 轮零增益；扩大池子只会扩大同一关键路径上的竞争。
4. **不要用 LLM 判断节点是否完成/是否该重试**。完成 = verifier 退出码（或 lean 门），重试 = `failureKind` 的封闭枚举。
   让模型「自评已完成」是把裁决权从运行时交出去，与 `research/gear-study.md` 的结论相反。
5. **不要用节点级成功替代轮级晋升**。recon 跑成功不等于 artifact 更好；promotion 仍只看 verifier + holdout +
   tests-clean + 超过该任务历史最好分。`gate.evaluated` 的字段一个都不该被节点事件改写。
6. **不要做「可回放性换速度」的任何事**：不跳过事件直接改 `views/state.json`（它必须能从账本重建）、不裁剪
   `events.jsonl`（dream-rsi 硬规则："删除绝不裁剪事件日志"）、不把 checkpoint 结论只留在内存。如果某条优化让
   「账本能回答的问题」变少，它的收益就是负的。
7. **不要给候选做 `Send` 式动态扇出**。LangGraph 的 `Send` 解决的是「扇出宽度由数据决定」，而我们的宽度由
   `candidates` 决定，是配置不是数据；现在做只会把一个数字变成一张图，收益为零。
