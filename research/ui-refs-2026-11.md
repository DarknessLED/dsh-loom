## 结论先行

1. 十个产品没有一个把「一次运行」画成我们这种「卡里塞树 + 柱 + 米 + chips」的混合体；它们只保留一种主视图，其余降级为悬停或点开。我们的信息量没错，缺的是**一种主视图 + 一条统一的「哪里出问题」的线**。
2. 阶段耗时：Dagster 用时间线、LangSmith 用 span 树加父聚合、GitHub 用 run→job→step 三级加失败自动展开；我们只有 chips 文本（1160 行），读者得在脑子里做除法——这是最便宜的一处改进（P1）。
3. 钱：LangSmith 给「父聚合 + 子细分 + 悬停明细」，GitHub 给 billable minutes；W&B、Dagster、Airflow 根本没有钱的概念。我们的 `costOf/costLabel` 已区分「未定价 / $0」（334/346 行），这条领先，别退回去。
4. 阈值：Grafana 默认 **80=red、Base=green（负无穷）、Absolute、Show thresholds 默认关**；阈值是读数层，不是装饰。我们的 75/100 两档方向对，缺的是「阈值写在哪」与「超限后怎么读」（P2）。
5. 「等你处理」：GitHub 把等批准叫 **"Waiting"**，30 天不批自动失败，Reject 会让 workflow 失败；Sentry 把 **For Review** 做成子集独立 tab 并按「离修好还差多少」分组；Temporal 用**连续 5 次**才报警过滤抖动。我们有 `waitMs/riskSource/deferred`，缺的是分组与批量（P3）。
6. 树 vs 时间线：Temporal 的 **Compact** 把 Activities/Signals/Timers 折成有名字的段——这是 320px 的正解：不删信息，只把一串事件变成几个名字（P4）。
7. 键盘：Raycast 让每个动作右侧标快捷键，Airflow 页脚常驻 `↑↓ ⏎ Esc`。我们已有 `hitProps/switchProps`（只吞 Enter/Space）与两处 `:focus-visible`，缺动作级快捷键与一行提示（P7）。
8. 重试：Airflow 用颜色 + tooltip 标 failed/retried，Temporal 只在连续 5 次后报警。我们的 8 根柱在染色，但「连续」这个维度没说出来（P8）。
9. 因此排序按「信息收益 ÷ 实现成本」：先补一条带（P1）、一条基线（P5）、一个阈值口径（P2），再谈批量与键位。
10. 不抄：多阈值配色、全宽甘特、可配置列、7 天季节性阈值、⌘K 全局面板——理由与失败模式见 §3。

## 1. 十一个产品，四个问题

### 1.1 LangSmith —— run 是 span，trace 是树

来源：<https://docs.langchain.com/langsmith/observability-concepts>、<https://docs.langchain.com/langsmith/cost-tracking>（读于 2026-11-08）

- **树 / 阶段耗时 / 重试** · run 被定义成「一个工作单元，类比 OpenTelemetry 的 **span**」；trace 是「一次操作的全部 runs，由 trace ID 绑定」。
- 三者对照表原文口径：Trace = **Tree of runs**，Thread = Sequence of traces，Trajectory = **扁平有序列表（抹掉嵌套）**。
- 同一份数据可以投影成树 / 序列 / 扁平三种——取决于读者此刻要回答的问题，而不是数据长什么样。
- 单条 trace 上限 25,000 runs；SaaS 保留 180 天。
- 「裁剪一个 run 的嵌套」被明确写成一种合法视图（Trajectory），不是缺省视图的残次品。

- **钱与预算** · 成本可自动（token × 模型价）或**手动**（任何 run 类型，含非 LLM 调用）。
- UI 把成本切成 **Input / Output / Other** 三类——不是一坨总额。
- **悬停成本区块出细分 tooltip**；trace 树里同时显示「整条 trace 总额 + 每个父 run 的聚合值 + 每个子 run 的细分」。
- 未定价可补：自定义 model price 条目；另有 evaluator 花费上限页。

- **等你处理** · 只取证到 feedback = tag + score 绑定单个 run（可按 run ID）；标注队列（annotation queue）官方页未取回，**未取证**，不作为依据。

- **键盘** · 这两页没有键位说明，**未取证**。

- **对我们的用处** · 「父聚合 + 子细分」：我们的 `待审` 分支只有条数（`meta: String(cps.length)`，1246 行），没有「这 N 条里最久等了多久」的聚合，也没有「哪条最急」的细分。

### 1.2 W&B Runs / Weave —— 表格 + 分组后的均值线与方差带

来源：<https://docs.coreweave.com/products/wandb/track/project-page>（读于 2026-11-08；`docs.wandb.ai` 已 301 到 CoreWeave）

- **钱与预算** · **没有钱的概念**。Project Details 的 Total compute = 所有 run 时长之和（时间，不是 $）。

- **等你处理** · 没有队列。侧栏顶部只显示总数「(183)」与「(N selected)」；没打开展示眼睛的 run 不进图。

- **键盘** · `Cmd+.` / `Ctrl+.` 收起或恢复 Runs 选择器；另有 keyboard shortcuts 专页被引用，本次未逐条取回。

### 1.3 Temporal UI —— 事件流、Compact 分组、连续 5 次才报

来源：<https://docs.temporal.io/web-ui>（读于 2026-11-08）

- **树 / 阶段耗时 / 重试** · History 四个视图：**Timeline**（正序/逆序，点事件看全字段）、All、**Compact**（原文「a logical grouping of Activities, Signals and Timers」）、JSON。
- 事件类型约 40 种；整份 history 可下载 JSON，也能导入本地 UI 重放。
- **Relationships** 是父子节点的完整层级树；**Pending Activities** 是独立 tab，页面上的摘要入口点一下跳过去。
- **Task Failures view**：**连续 5 次** workflow task 失败或超时才标记，恢复一次成功即清除。
- 阈值来自 `system.numConsecutiveWorkflowTaskProblemsToTriggerSearchAttribute`，默认 5，设 0 关闭；官方理由就是过滤小抖动、只暴露真问题。

- **钱与预算** · 只有 **Billable Actions Count**（仅 Cloud）。没有预算条、没有阈值、没有「超支」概念。

- **等你处理** · Pending Activities（等 worker/等信号）+ Task Failures 预置 Saved View；**没有**「批准/驳回」这类人工决策队列。

- **键盘** · 取证到的是时间格式可切 UTC / Local / **Relative**；Saved Views 最多 20 个、存浏览器本地、可分享 URL；键位表**未取证**。

- **对我们的用处** · Compact = 320px 的正解：P4 把「失败」从 meta 行提升成一个有名字的分支，就是同一种折叠。
- Relative 时间：我们 `age()` 已经是相对口径（356 行），可以直接用在 P6 的新鲜度上。

### 1.5 Airflow —— Grid：行是 task，列是 run

来源：<https://airflow.apache.org/docs/apache-airflow/stable/ui.html>（读于 2026-11-08）

- **树 / 阶段耗时 / 重试** · Grid View **行 = task、列 = Dag run**；悬停任一 task instance 出详情。
- 原文「identify failed or retried tasks by **color and tooltip**」——颜色必须配 tooltip，否则色盲与非色盲都不知道具体原因。
- 点 cell 可看日志，也可手动标记 success / failed / cleared。
- 顶部可选「last 25 runs」这样的范围；Runs tab 是可排序表，列含 status、**execution duration**、run type、Dag version。
- Dag 详情有 Versions 对比（3.4 新增）：逐条列 changed path，**把影响执行的改动（如 operator、retries）与纯元数据改动分开标注**。

- **钱与预算** · 没有。

- **等你处理** · 没有审批队列；人工介入是「标记 cell 状态」与「pause/resume Dag」。

- **键盘** · 搜索 ⌘+K（advanced search）；页面底部常驻提示 `↑↓ Navigate ⏎ Select Esc Close`。

- **对我们的用处** · 颜色 + tooltip 是一对：我们已有 `title`，缺图例与「重试」这个状态词（P8 的连续计数）。
- 「影响执行的改动 vs 纯元数据」的区分，对应我们的「有风险评估 vs 未评估」。

### 1.6 GitHub Actions —— run → job → step，失败的 step 自动展开

来源：<https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs>、<https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments>（读于 2026-11-08）

- **树 / 阶段耗时 / 重试** · 层级由 Checks API 定义：**一次 workflow run = 一个 check suite，每个 job = 一个 check run，每个 job 内含 steps**。
- run 页显示 in progress/complete 与 success/failure/canceled/neutral；**失败的 step 自动展开**。
- 「可以看每个 step 花了多久」；点日志行号得永久链接；**日志搜索只搜已展开的 step**（搜索范围跟可见性绑定）。
- 可下载 log archive；部分重跑时 archive 只含重跑过的 job。
- 每个 job 额外注入 "Set up job" 与 "Complete job" 两个 step——基础设施开销也在 step 列表里，所以 step 时间含准备成本。

- **钱** · run 页可看 **billable job execution minutes**。

- **等你处理** · 等人工批准的 job 状态就叫 **"Waiting"**；**30 天不批自动失败**。
- Review deployments → 勾环境 → 可留评论 → **Approve and deploy / Reject**，**Reject 会让 workflow 失败**。

- **键盘** · 这两页未写键位，**未取证**。

- **对我们的用处** · 「默认展开失败的那一支」是被 GitHub / Dagster / Sentry 三家共同采用的手法：成本低、收益直接（P4）。

### 1.8 Sentry —— For Review 是 unresolved 的子集；配额与 spike

来源：<https://docs.sentry.io/product/issues/>、<https://docs.sentry.io/pricing/quotas/spike-protection/>（读于 2026-11-08）

- **树 / 阶段耗时 / 重试** · 问题流是**行**不是树；事件详情时间线页本轮未取回，**不作依据**。

- **钱与预算** · 按**月度事件数**计费。
- Spike 阈值取两者较大值：(a) 由配额推出的最小事件数；(b) **过去 168 小时（7 天）**加权投影（含小时/星期季节性）× **5 倍标准差**（系数夹在 3–6）。
- **spike 持续期间每小时重算**阈值；被丢弃事件的贡献按指数衰减计入（24 小时后约 10% 权重、48 小时后≈0）。
- 触发后动态限流丢事件；通知要单独配（Sentry/Slack/PagerDuty/Opsgenie）；建议配 pay-as-you-go budget。

- **等你处理** · **For Review**（`is:unresolved is:for_review`）是 unresolved 的子集、独立 tab。
- 每行固定三段「类型与描述 / 所属项目 / first–last seen」。
- 排序有 Recommended / Last Seen / First Seen / Trends / Events / Users；Trends 规则公开（相对量、绝对量、**年龄指数衰减每 12 小时折半**）。
- Inbox 按「离修好还差多少」分组。

- **键盘** · 未取证。

- **对我们的用处** · 「子集独立 tab + 稳定三段式行 + 公开的排序规则」。我们的队列行已是三段（战役 · 类型 — summary），缺的是公开排序说明（现按 risk→deferred→campaign→id，读者看不出来）。

### 1.10 Grafana —— 阈值默认 80 红、Base 绿，可染文字或背景

来源：<https://grafana.com/docs/grafana/latest/panels-visualizations/configure-thresholds/>（读于 2026-11-08；canonical 现为 `/docs/grafana/latest/visualizations/panels-visualizations/configure-thresholds/`）

- **树 / 阶段耗时** · 没有 run 树。表格单元格支持 `TableCellDisplayMode = sparkline`（<https://grafana.github.io/grafana-foundation-sdk/go/Reference/common/object-TableCellDisplayMode/>），把 8 个点压进一格；表格还能用彩色文字 / gauge / 色块「many variables at a glance」（<https://docs.enlyze.com/en/integrations/grafana/visualisation-types/03-tables>）。

- **钱与预算 / 阈值** · 默认 **80 = red**、**Base = green（代表负无穷）**、Mode = **Absolute**、Show thresholds 默认关。
- 另有 **Percentage** 模式（相对 min/max）。
- 可染：表格的**单元格文字或背景**、gauge 与 threshold marker、state timeline 区域、time series 的线/色带。
- 显示形式 lines / dashed / filled regions / both；阈值数量不限，**自动从高到低排序**。

- **/ Q4** · 没有队列；键位未取证。

- **对我们的用处** · 阈值是可关闭的读数层。我们的 `meterOf` 把 75%/100% 硬编码进 tone（1085 行），从没对外说过这两个数——超限时读者不知道为什么变红。

### 1.11 Raycast —— Action Panel：动作右侧标快捷键

## 2. 八条提案（表按 信息收益 ÷ 实现成本 排序；小节按 id 展开便于查找）

| 序 | id | 组件 | 一句话 | 新增纯函数 | 成本 |
|----|----|------|--------|-----------|------|
| 1 | P2 | 指标条 | ≤360px 只留 3 个「要处理」的数 | `metrics().priority` | S |
| 2 | P5 | 卡（spark） | 加一条在任者基线 | `sparkOf().ref` | S |
| 3 | P8 | 卡头 | 连续未晋升 ≥3 才提示 | `streakOf` | S |
| 4 | P6 | 顶栏 | 数据新鲜度：区分「没变化」与「没读到」 | `freshness` | S |
| 5 | P4 | 树 | 失败分支置顶并默认展开 | `treeOf` 内 `fail` 分支 | M |
| 6 | P1 | 卡（树上方） | 一行按耗时占比分段的运行带 | `nodeBand` | M |
| 7 | P3 | 队列 | 按战役分组 + 低风险批量批准 | `queueOf().groups` | M |
| 8 | P7 | 顶栏/动作区 | 动作级快捷键 + 一行提示 + 焦点环 | `shortcutHints` | L |

> 每条都写明：改什么 / 证据（案例或规范条款 + URL）/ 机械验证（哪个测试文件、哪个纯函数、断言长什么样）/ 收益（可量化）。

### P2 · 指标条只留「要处理」的三个数（≤360px）

**改什么**

- `metrics()`（511 行）每格加 `priority: 'primary' | 'secondary'`：primary 固定 `running / pending / spend`，secondary 为 `campaigns / rounds / lessons`。
- `Panel` 渲染（1509–1521）写 `data-priority`；CSS 在 `@media (max-width:360px)` 内 `display:none` 掉 secondary。
- 现有 320px 规则（286 行）只是把 6 格改成 3 列 × 2 行，仍然是两行——这条是把它压成一行。

**证据**

- Grafana：阈值是可关的读数层，默认 Show thresholds = Off（<https://grafana.com/docs/grafana/latest/panels-visualizations/configure-thresholds/>）。
- W&B：明确区分「总数 / 选中 / 实际画出」（<https://docs.coreweave.com/products/wandb/track/project-page>）。
- Vercel：部署列表按 status 过滤而不是全量滚（<https://vercel.com/docs/deployments/managing-deployments>）。

**机械验证** `tests/ui/metrics-priority.test.mjs`

- `metrics(payload).length === 6`；`filter(m => m.priority === 'primary').map(m => m.key)` 深等于 `['running','pending','spend']`。
- 6 格的 key 集合不变（防止顺手删格）。
- 源文本正则：存在 `@media (max-width:360px)`，且块内含 `.loom-metric[data-priority="secondary"]{display:none}`。
- 观测项（不进断言）：320 画布跑 `scripts/panel-audit.mjs` 时 `.loom-metrics` 高度 ≤ 单行。

**收益**

- 320px 下指标条从约 38px 降到约 19px，首屏多露半行队列；三个只增不减的数不再和「待处理」抢位置。

### P5 · spark 加一条在任者基线

**改什么**

- `sparkOf(c)`（1035 行）返回 `ref`：`c.incumbent.score` 是有限数且 `max > 0` 时 `{score, pct: Math.round(score / max * 100), title:'在任者 ' + score}`，否则 `null`。
- `.loom-spark`（1882 起）内加绝对定位的 1px 横线 `data-ref`，`bottom: pct%`；容器 title 追加「线 = 在任者分数」。

**证据**

- W&B 分组后图里出现均值线 + 方差带（<https://docs.coreweave.com/products/wandb/track/project-page>）。
- Grafana：Base 阈值代表负无穷，基线在其模型里是一等公民（<https://grafana.com/docs/grafana/latest/panels-visualizations/configure-thresholds/>）。
- LangSmith：父聚合与子细分并置（<https://docs.langchain.com/langsmith/cost-tracking>）。

**机械验证** `tests/ui/spark-ref.test.mjs`

- 窗口最高 0.9、`incumbent.score = 0.8` → `ref.pct === 89`。
- 无 incumbent → `ref === null`（不是 0，避免画一条贴底的假线）。
- 全 0 分窗口（`max` 被钳到 1）→ `ref.pct === 0` 且 `ref.score === 0`。
- 渲染断言：`.loom-spark` 子元素里恰有一个 `[data-ref]`，`style.bottom === ref.pct + '%'`。

**收益**

- 柱高现在只表示「相对本窗口最高」，读者无法判断「这轮比在任者好吗」；一条线消掉把回退看成进步的误判。

### P8 · 连续未晋升 ≥3 才提示

**改什么**

- 新增 `streakOf(c)` → `{count, label}`：从 `trendOf(c)` 末尾向前数 status ∈ `no-gain / holdout-failed / crashed / failed / exhausted` 且 `promoted !== true` 的轮；遇到 `promoted` 或未知状态停止。
- `count >= 3` 时卡头（1830 起的 `loom-titlerow`）渲染 `.loom-flag`「连续 N 轮未晋升」，title 写「从第 X 轮起」。

**证据**

- Temporal：连续 5 次失败/超时才标记，恢复一次成功即清除；阈值默认 5、可设 0 关闭，官方理由是过滤小抖动（<https://docs.temporal.io/web-ui>）。
- Airflow：failed or retried 用颜色 + tooltip 标出，重试是独立状态（<https://airflow.apache.org/docs/apache-airflow/stable/ui.html>）。

**机械验证** `tests/ui/streak.test.mjs`

- 3 轮 `no-gain` → `count === 3` 且 `flag === true`。
- 2 轮 `no-gain` → `flag === false`（不提示）。
- 序列 `[no-gain, promoted, no-gain]` → 截断为 1（promoted 是硬边界）。
- `trendOf(c) === null` → `{count: 0, flag: false}`，不抛错。
- 源码正则：函数体内无 `Date.now`（纯函数，时间不参与）。

**收益**

- 单轮抖动不再看起来像连败；巡检时一眼区分「偶发」与「真的卡住」，减少一次翻 spark 柱子数状态的次数。

### P6 · 顶栏新鲜度：区分「没变化」与「没读到」

**改什么**

- 新增 `freshness(updatedAt, now)` → `{text, stale, ageMs}`；`stale = ageMs > 2 * POLL_MS`（10000ms）。
- `updatedAt` 非有限数 → `{text:'未知', stale:true, ageMs:null}`。
- 顶栏刷新按钮左侧渲染 `<span class="loom-fresh" data-stale={stale}>`，文本用 `age()` 口径（356 行），title 写「最后一次读到数据的时间；超过 10 秒算陈旧」。

**证据**

- Temporal：时间格式可切 **Relative**，页头固定 Start/Close/Duration（<https://docs.temporal.io/web-ui>）。
- Sentry：行内固定「first–last seen」，时间与对象同屏（<https://docs.sentry.io/product/issues/>）。
- Vercel：构建日志用黄/红区分 warning/error（<https://vercel.com/docs/deployments/logs>）。

**机械验证** `tests/ui/freshness.test.mjs`

- `freshness(now - 11000, now).stale === true` 且 `text === '11秒'`。
- `freshness(now - 3000, now).stale === false`。
- `freshness(undefined, now)` → `stale === true`、`text === '未知'`、`ageMs === null`。
- 源码正则：函数内不得出现 `Date.now`。

**收益**

- 轮询静默失败（fetch 抛错但保留旧 `data`）时，读者现在看到的是「和上次一样」；加陈旧标记后，误判「循环卡住了」的情况减少。

### P4 · 失败分支置顶：`fail` 成为树的第一行

**改什么**

- `treeOf(c, live, corpus)`（1311 行）在 `lastRound.status ∈ {crashed, failed, holdout-failed, interrupted}` 时插入 `{key:'fail', label:'失败', meta: 状态 + 分数 + taskId, tone: bad, children: 被筛除/放弃的 attempts}` 作为首节点。
- 成功路径不变：`round` 仍在最前，避免「每张卡第一行都是失败」的误读。
- 同时把 `waitingNode` 的 `meta`（1246 行）从纯条数改成 `N 条 · 最久 12 分`，数据直接取 `pending()` 已算的 `waitMs`（659 行）。

**证据**

- GitHub：失败的 step 自动展开，run→job→step 三级（<https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs>）。
- Dagster：问题 step 标红并单列 Errored 区块（<https://github.com/dagster-io/dagster/blob/3d211efd50c6c5e9323315f6b674ecdb58849ae9/docs/dagster-university/pages/dagster-essentials/lesson-3/viewing-run-details.md>）。
- Temporal：Compact 视图把同类事件折成有名字的段（<https://docs.temporal.io/web-ui>）。

**机械验证** `tests/ui/tree-fail-first.test.mjs`

- `treeOf({lastRound:{n:7,status:'holdout-failed',score:0.41,attempts:[]}})[0].key === 'fail'`，`meta` 含 `0.41`。
- 健康 payload（`status:'promoted'`）首节点仍是 `'round'`。
- `waitingNode` 两检查点 `waitMs` 为 12000 / 900000 → `meta === '2 条 · 最久 15 分'`。
- `treeLines` 首行以 `├─ 失败` 开头（或 `└─` 当唯一节点），保证文本投影同步。

**收益**

- 失败原因从「点开卡 → 找到 meta 行 → 读一长串」变成「打开卡第一行就是」；每轮都失败的战役，每次巡检少 2 次点击。

### P1 · 运行带：把「5 个数字」变成「1 条按比例分段的带」

**改什么**

- 卡内、树上方新增 `<div class="loom-band">`：100% 宽、8px 高，按 `c.nodes` 各自 `durationMs` 占比切段。
- 每段 `title="规划 4分1秒"`；`data-tone` 沿用 `nodeChips` 规则（done=ok / lost=bad / 其余 warn）。
- 纯函数 `nodeBand(c)` → `{total, unknown, segments:[{key,label,ms,pct,tone,title}]}`；`pct` 用最大余数法分配，和恰好 100。
- `nodes` 缺失 → 函数返回 `null`；只有 1 段时函数照常返回对象，「少于 2 段不渲染」是渲染层的决定（一条带没有比较对象时是噪音）。

**证据**

- Dagster：run timeline 显示每个 step 何时执行、耗时多少，问题 step 标红（<https://raw.githubusercontent.com/dagster-io/dagster/refs/heads/master/docs/docs/guides/operate/webserver.md>）。
- GitHub：「可以看每个 step 花了多久」（<https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs>）。
- LangSmith：run 是 span，时长是 span 的一等属性（<https://docs.langchain.com/langsmith/observability-concepts>）。

**机械验证** `tests/ui/node-band.test.mjs`

- `sum(segments.map(s => s.pct)) === 100` 且每段 `pct >= 1`。
- 时长 3:1 的两节点 → `pct` 为 `[75,25]`（±1）。
- `durationMs` 缺失的节点进 `unknown` 而不是 0；全缺失 → `nodeBand(c) === null`。
- 渲染断言：`Card(react)({c})` 的元素树里 `.loom-band` 的 children 数等于 `segments.length`，且每段有非空 `title`。

**收益**

- 「这轮时间花在哪」从「读 5 个 chip 再心算」变成 1 次扫视；4 个节点以上的链，判断瓶颈少 1 次点击加约 5 秒心算。

### P3 · 队列按战役分组 + 只在低风险时给批量批准

**改什么**

- `queueOf`（696 行）增加 `groups: [{campaign, rows, count, earliestWaitMs, bulkAllowed}]`。
- `bulkAllowed` 为真当且仅当组内每行都 `riskSource === 'review'` 且 `risk !== 'high'` 且未 `deferred`——未评估不允许批量（宿主没看过风险，人不能替它批量点头）。
- 渲染：组头一行「campaign · N 条 · 最早等 12 分」，右侧「全部批准」，复用 `confirming` 做二次确认。
- 队列行补上「暂缓」按钮（decision 'hold'），与树里 `waitingNode` 的三个动作（1261–1265 行）对齐。

**证据**

- Sentry：For Review 是子集独立 tab，Inbox 按「离修好还差多少」分组，排序规则公开（<https://docs.sentry.io/product/issues/>）。
- GitHub：Review deployments 可一次勾选多个 environment 再 Approve（<https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments>）。
- Linear：同一动作在三处位置不一致就是问题（<https://linear.app/now/behind-the-latest-design-refresh>）。

**机械验证** `tests/ui/queue-groups.test.mjs`

- 3 个战役各 1 条 → `groups.length === 3`，每组 `count === rows.length`。
- 组内含一条 `riskSource:'default'` → `bulkAllowed === false`；含 `risk:'high'` → `false`。
- 两条 `normal` 且都来自 review → `true`；`earliestWaitMs === Math.max(两条 waitMs)`（最早等的是**最大**等待，别写反）。
- `pending(...)[0].actions` 含 `'snooze'`（与渲染后的按钮数一致，3 个）。

**收益**

- 同战役 2 条以上待审时，一次批准替代 N 次点击；「未评估」不再被批量吞掉——这是安全边界，不是 UI 喜好。

### P7 · 动作级快捷键 + 一行提示 + 全量焦点环

**改什么**

- 新增 `shortcutHints(hasQueue)` → 固定顺序 `[{key:'J',label:'下一条'},{key:'K',label:'上一条'},{key:'Enter',label:'展开'},{key:'A',label:'批准'},{key:'X',label:'驳回'},{key:'S',label:'暂缓'},{key:'Esc',label:'取消'}]`；`hasQueue === false` 时去掉 A/X/S。
- `Panel` 在 `.loom-scroll` 底部渲染一行 9.5px 提示；队列行与树行的 `title` 末尾追加 `（A）` 这类后缀。
- `focus-visible` 从现有 `.loom-hit` / `.loom-btn` / `.loom-switch` 扩到 `.loom-row` 与 `.loom-node .acts .loom-btn`。
- 键位只在 `.loom-scroll` 内、且 `document.activeElement` 不是 input/textarea 时生效；只吞上表列出的键（沿用 `hitProps` 的「只吞两个键」纪律）。

**证据**

- Raycast：Action Panel 列出全部动作，每个动作右侧标快捷键（<https://manual.raycast.com/action-panel>）。
- Airflow：页脚常驻 `↑↓ Navigate ⏎ Select Esc Close`（<https://airflow.apache.org/docs/apache-airflow/stable/ui.html>）。
- Linear：动作位置不可预测是产品被功能挤变形的证据（<https://linear.app/now/behind-the-latest-design-refresh>）。

**机械验证** `tests/ui/shortcuts.test.mjs`

- `shortcutHints(false).map(h => h.key)` 不含 `'A'/'X'/'S'`；`shortcutHints(true)` 全含。
- 每项 `key` 唯一；数组长度 7 / 4（防「加键不加处理」）。
- 渲染断言：队列行 `.loom-row` 的 `title` 以 `（A）` 或 `（X）` 结尾。
- CSS 正则：`.loom-row:focus-visible` 与 `outline-offset` 存在，且全文 `outline: none` 计数为 0（沿用 a11y spec 写法）。

**收益**

- 键盘用户每处理一个检查点少一次鼠标定位；对只用键盘的人，这是「能不能用」而不是「快不快」。风险最高：全局 keydown 会与宿主输入框抢键，所以限定容器与键集。

## 3. 五条不要抄

### 3.1 不要抄 Grafana 的多阈值配色 + 图例

- 它服务「连续时间序列里找越界点」；我们只有 8 根柱、4 个色 token。
- 加第二条阈值线就要加颜色和图例，直接违反「≤4 色」与 `scripts/panel-audit.mjs` 的对比度下限（<13px 文本 3.8）。
- 阈值只保留 `budgetMeters` 的 75/100 两档，写进 title 就够。

### 3.2 不要抄 Dagster/Gantt 的全宽时间线

- 320px 下 8 个节点每段约 36px，标签放不下，必然换行或被截断。
- `panel-audit` 会把未 clamp 的溢出直接判 FAIL（248 行脚本，FAIL 条件 226–242）。
- P1 的「一条带 + 悬停看数字」是同一信息在 320px 的上限。

### 3.3 不要抄 W&B 的可配置列（pin / hide / group by）

- 侧栏没有「列」，只有堆叠行；配置化意味着持久化布局状态、处理「布局丢了」的投诉。
- 收益只是「把不常看的字段藏起来」。要藏就按优先级固定藏（P2）。

### 3.4 不要抄 Sentry 的动态阈值（7 天季节性 × 5σ）

- 那算法需要每小时成千条事件才有统计意义；我们一个战役 8 轮、可能一天 3 轮。
- 任何「动态阈值」都会随噪声跳。Temporal 的「连续 5 次」是能用的最简形式，P8 降到 3 并在文案里说清「连续」。

### 3.5 不要抄 Linear/Raycast 的 ⌘K 全局面板

- 面板没有自有路由，⌘K 在宿主里已被占用；再挂一个会抢键，还要维护「命令 → 动作」注册表。
- P7 的局部 j/k + Esc + 一行提示能拿到 80% 收益，冲突面小一个数量级。

## 4. 落地顺序与冲突面

八条提案落在五个互不重叠的渲染区域里，可以按区域分批落地，避免同一次改动碰三处：

| 批次 | 区域 | 提案 | 触碰的现有代码 | 与既有 spec 的关系 |
|------|------|------|----------------|--------------------|
| 1 | 顶栏 | P2、P6 | `metrics()` 511、header 1490–1507、CSS 116/286 | 不改 `metrics` 的 6 个 key，`tones`/`a11y` 不受影响 |
| 2 | 卡头与 spark | P5、P8 | `sparkOf` 1035、`loom-titlerow` 1830、CSS 187–198 | 必须保住 `spark-baseline` 已有的 `px` 语义（unknown=0、zero=2） |
| 3 | 树 | P4 | `treeOf` 1311、`waitingNode` 1240、`treeLines` 1349 | `node-attribution` 与 `checkpoint-help` 的断言要跟着改期望 |
| 4 | 卡身 | P1 | 卡身渲染 1983–1997、CSS 新增 `.loom-band` | 独立，无既有断言 |
| 5 | 队列 | P3 | `queueOf` 696、队列渲染 1603–1676 | `pending-queue` / `snooze` / `queue-total` 三条会重叠，先读再改 |
| 6 | 键位 | P7 | `Panel` 顶部 effect、底部提示、CSS `:focus-visible` | `keyboard-hit` / `a11y` 的键位纪律必须原样保留 |

两条硬约束（来自现有测试与审计脚本，不是本文的偏好）：

- **不许引入第五个颜色**：`a11y.test.mjs` 会算对比度，`tones` 把四色写死；P5/P8 的新标记只能用 `var(--loom-*)`。
- **不许让几何退化**：`scripts/panel-audit.mjs` 在 320/400/720 三个画布上量横向溢出、未 clamp 的文本、列数与阴影；P1 的带、P2 的隐藏、P4 的长分支都必须先在 320 画布通过。

## 6. 附：三条断言的写法草案

以下不是最终测试，只是把「机械验证」落到 `tests/ui/harness.mjs` 的现有范式上；`ok(...)` 沿用各 spec 里自己那个打印 `ok N - name` 的小函数，`loadPanel()` 返回 `__panel`。

```js
// tests/ui/node-band.test.mjs（P1）
import { loadPanel } from './harness.mjs'
const panel = await loadPanel()

const band = panel.nodeBand({
  nodes: [
    { id: 'n1', role: 'planner', status: 'done', durationMs: 90000 },
    { id: 'n2', role: 'agent', status: 'done', durationMs: 30000 },
  ],
})
ok('pct 之和恰好 100', band.segments.reduce((s, x) => s + x.pct, 0) === 100)
ok('时长 3:1 切成 75/25', band.segments.map((x) => x.pct).join(',') === '75,25')
ok('每段至少 1%', band.segments.every((x) => x.pct >= 1))
ok('无节点返回 null', panel.nodeBand({ nodes: [] }) === null)
ok('缺 durationMs 记 unknown 而不是 0', panel.nodeBand({ nodes: [{ id: 'x', status: 'done' }] }).unknown === 1)
ok('丢失节点 tone 为 bad', panel.nodeBand({ nodes: [{ id: 'l', status: 'lost', durationMs: 1 }] }).segments[0].tone === 'bad')
```

```js
// tests/ui/queue-groups.test.mjs（P3）
import { loadPanel } from './harness.mjs'
const panel = await loadPanel()
const now = 1_000_000
const cp = (id, at) => ({ id, kind: 'gate', at })
const rv = (id, risk) => ({ id, kind: 'gate', risk, summary: 's' })

const data = {
  campaigns: [
    { id: 'a', open: 2, openCheckpoints: [cp('c1', now - 900000), cp('c2', now - 12000)], reviews: [rv('c1', 'normal'), rv('c2', 'normal')] },
    { id: 'b', open: 1, openCheckpoints: [cp('c3', now - 1000)], reviews: [] },
  ],
}
const q = panel.queueOf(data, { now })

ok('两个战役两组', q.groups.length === 2)
ok('a 组两条', q.groups.find((g) => g.campaign === 'a').count === 2)
ok('最早等 15 分（取最大 waitMs）', q.groups.find((g) => g.campaign === 'a').earliestWaitMs === 900000)
ok('a 组可批量（全部已评估且非 high）', q.groups.find((g) => g.campaign === 'a').bulkAllowed === true)
ok('b 组不可批量（未评估）', q.groups.find((g) => g.campaign === 'b').bulkAllowed === false)
ok('队列行三个动作', panel.pending(data, { now })[0].actions.length === 3)
```

写这些断言时注意两件事：一是 `queueOf` 的 `now` 必须显式传入（现有实现已支持，616 行），否则 `waitMs` 会在跨秒时抖；二是 `groups` 的排序要与 `pending` 的行序一致，别另立一套（否则组头和组内第一条会指向不同对象）。
