# R1：子会话死亡与失败分型（2026-11 调研）

> 只回答一件事：子会话结束了，我们能不能说出**为什么**、该按什么分类处理、阈值取多少。
> 所有外部引用读于 2026-11-11；所有本地数字读于 2026-11-11 的 `~/.dsh/loom/campaigns/*/events.jsonl`（22 个战役、418 条 `attempt.finished`）。
> 一句话结论：我们缺的不是「死亡检测器」，是「死亡归因」。`died` 一个词吃掉了四种互斥事件；而唯一像检测器的东西，是把「没有证据」当成「基础设施故障」的证据。

## 0. 先纠正三件事

**M1｜代码里没有「elapsedMs < 3000ms 就判 infra」这条规则。**
`src/dispatch/session.js:411` 就是一行 `const infra = silent`；`silent` 在 `:403` 定义为 `stopReason === 'error' && !diagnostic`，与耗时**无关**。`elapsedMs` 只在 `:392` 与 `:395` 计算，随后整条丢弃——`round.js` 从不读 `res.elapsedMs`（全仓 grep 只有 session.js 命中），attempt 记录里也没有这个字段。
→ 「3 秒内静默死亡」是事后**相关性**，不是判据。我们要么把它变成判据，要么别在复盘里用它。

**M2｜`died` 不是一种死法，是四种。**
145 条 died 的 `stopReason`：`error` 106、`aborted` 39。39 条 aborted 里 28 条带 `abandoned:true`（多数是 `solved-by-sibling`，`round.js:1481`），另有 11 条只有 `stopReason:'aborted'` 而无 abandoned 标记。此外还有 9 条 `crash` 走完全不同的路径（`lostToDisposal`，`round.js:68-72`，要求错误文本匹配 `/dispatcher\s+disposed/i`）。
→ 同一个字段里混着「被兄弟杀了」「被 campaign 停了」「自己断了」「宿主重启了」。

**M3｜145 条 died 没有一条带回可读诊断。**
`error` 等于占位串 `child session ended in error with no diagnostic (parent or provider unavailable)` 的 80 条（占位串在 `session.js:418-421` 生成），为空的 65 条（旧 schema 根本不写该字段）。
注意一个陷阱：`diagnosisSource:'session-log'` 在 `session.js:424` 被返回，但 **`round.js` 从不把它写进账本**——所以「账本里 `diagnosisSource` 命中 0 次」**不能**证明 `#sessionDiagnosis()`（`:433-439`）一次都没救回消息，只能证明**唯一能说明诊断来源的字段被丢弃了**。这本身就是一个可修的观测缺口。

### 145 条 died 的形状

| 观察 | 值 | 含义 |
|---|---|---|
| `durationMs` < 1s / 1–3s | 约 60 / 33（合计 93 条 < 3s） | 根本没起来 |
| 3–10s | 5 | 断层 |
| ≥ 10s（最长约 350s） | 47 | 跑了很久才断 |
| 带补丁（`patchBytes > 0`） | 33 | 它干过活 |
| `infra:true` / `infraRetry:true` | 32 / 32 | 见 §3 E2 |
| `abandoned:true` | 28 | 是我们杀的 |
| 全量「有补丁但无裁决」 | 72 / 418 | 见 §3 E3 |

双峰是要紧的：如果死亡是单一原因（provider 挂了），时长应集中在某个连接超时附近。93 条在 3 秒内、47 条在 10 秒以上、中间只有 5 条——这是**两类事件**，今天写成了同一个词。
→ 落点：`src/dispatch/session.js:403,411`；`src/runtime/round.js:84-88`；`src/core/config.js:57`（`attemptTimeoutMs: 10 * 60_000`）。

## 1. 业界到底怎么判「死了」还是「慢」

### 1.1 Temporal：不检测，只超时 + 心跳
四种超时：Schedule-To-Start / Start-To-Close / Schedule-To-Close / Heartbeat。原文：

> "The Temporal Server doesn't detect failures when a Worker loses communication with the Server or crashes. Therefore, the Temporal Server relies on the Start-To-Close Timeout to force Activity retries."

即：它**不**试图分辨「没消息」和「死了」，而是用 Start-To-Close 超时强制重试；且 Start-To-Close "has no default value of its own"——必须由调用方按最长执行时间设定。
心跳才是进度信号："a ping ... that the Activity Execution is making progress and the Worker has not crashed"；长任务建议 "relatively short Heartbeat Timeout and a frequent Heartbeat"；心跳节流间隔 = `min(heartbeatTimeout * 0.8, maxHeartbeatThrottleInterval)`，`defaultHeartbeatThrottleInterval = 30s`、`maxHeartbeatThrottleInterval = 60s`。
→ 落点：我们已经有心跳源（子会话 `seq` 水位，`watchdog.js:118-125`），但只用来在 5 分钟后杀人（`config.js:84` 的 `stallMs`），从不入账。

### 1.2 gRPC：连接存活 ≠ 服务健康，而且默认几乎不开
客户端 `KEEPALIVE_TIME` 默认 `INT_MAX`（等于关闭），服务端 `7200000`（2h）；`KEEPALIVE_TIMEOUT` `20000`（20s）；`PERMIT_KEEPALIVE_TIME` `300000`（5min）；建议 "avoid configuring their keepalive much below one minute"。
明确区分："Health checking allows a server to signal whether a service is healthy while keepalive is only about the connection."
→ 落点：我们的 `infra` 是「进程还活着吗」级别的信号，却被当成「provider 健康吗」使用——这正是 gRPC 文档点名的那两个概念被混淆。

### 1.3 Kubernetes：三种探针，语义不同，动作不同
- liveness 失败 → kubelet 杀掉并重启容器；
- readiness 失败 → "the pod will be marked unready and will not receive traffic"（**不杀**）；
- startupProbe `failureThreshold: 30` × `periodSeconds: 10` = 300s 启动宽限，"If the startup probe never succeeds, the container is killed after 300s"；
- "The readiness and liveness probes do not depend on each other to succeed."
→ 落点：可直接借的结构是「起来得慢」与「已经死了」用不同阈值、不同动作。我们只有一个 `stallMs`。

### 1.4 SSE：断流是可重连事件，不是死亡
EventSource 自带 reconnection time（"probably in the region of a few seconds"）；重连带 `Last-Event-ID` 游标续传；"Clients will reconnect if the connection is closed; a client can be told to stop reconnecting using the HTTP 204 No Content response code."
→ 落点：如果子会话是流式的，断流应当先试「从游标续」，而不是记一次 died。宿主支持续跑（`research/dsh-plugin-api.md:158-184` 的 `startActivation({childId})`、`agentLoop.resume({resumeSessionId})`），我们没用。

### 1.5 失败分类学：MAST
arXiv:2503.13657（v3，2025-10-26）：1600+ traces、7 个框架、150 条人工标注（kappa=0.88）→ **14 种失败模式、3 大类**：system design issues / inter-agent misalignment / task verification。
→ 落点：多代理失败的大头**不在**「模型死了」。我们的 `died` 占 34.5%，而其中 33 条留下了补丁——provider 故障不会产补丁，这条自相矛盾本身就是分类错误的证据。

### 1.6 重试的经济学：AWS Builders' Library
- 超时怎么选：先定可接受误超时率（如 0.1%），再取该比例对应的下游延迟分位（如 p99.9）；
- 五层调用各 3 次重试 = 243× 放大，所以 "retry at a single point in the stack"；
- 只在「观察到底层健康」时重试："We avoid this amplification by retrying only when we observe that the dependency is healthy."；
- circuit breaker 引入模态行为并拖慢恢复，Amazon 更偏好 token bucket 限流重试；重试需 capped exponential backoff + jitter，且副作用接口必须幂等。
→ 落点：这条直接否掉 `session.js:214-218`——`infra` → `rebuildParent()` → **同模型**重发一次。我们没有观测到 provider 健康，只观测到「没消息」。

### 1.7 长思考的反例
Anthropic extended thinking：thinking 发生在 "before it starts its final answer"；`budget_tokens` 最小 1024 且必须小于 `max_tokens`；"higher budgets ... at the cost of increased latency"；"Pushing the model to think beyond 32k tokens produces long-running requests that can hit system timeouts and open-connection limits."
→ 落点：49 秒以上的静默在合法工作范围内；任何「N 秒无输出=坏」的规则都必须先排除长思考。

## 2. 该分几类：六类封闭枚举 + 默认动作

| class | 机械判据 | 默认动作 | 阈值 / 依据 |
|---|---|---|---|
| `deadline` | 我们到点自己杀（今天 `failureKind:'timeout'`） | 不重试；记 `killReason:deadline` | `session.attemptTimeoutMs` 600s |
| `silent-no-signal` | 子会话从未出现事件（`lastSeq` 始终 null），且 grace 内以 error 结束 | 不重建父；换 provider；同 provider 冷却 | grace 90s（≈健康首信号 p99，需测） |
| `silent-after-progress` | 有过事件，但 turn 以 error 结束且无诊断 | 重试一次（可换模型），标 `unexplained` | 不设秒数，看事件数 |
| `stalled` | watchdog 判 `idleMs > stallMs` 后 abort（今天只进内存 `runtime.stalls`） | 记 `killReason:watchdog` + 心跳证据 | `session.stallMs` 300s |
| `killed` | 我们主动 abort：兄弟成功 / campaign 停 / human stop | 不重试；**不计入任务证据** | — |
| `bad-output` | turn 完成但 structured 解析失败 / tool-call JSON 粘连 | 重试一次，标 `protocol` | 由 `reportError` 计数 |

关键：`died` 不再是叶子类，而是 rollup（`died = silent-* | stalled | killed | protocol`）。这与 MAST 的层次一致——先分「谁的错」，再分「怎么错」。

## 3. 现在的判据错在哪（每条给证伪方法）

**E1 因果倒置。** `infra = silent`：用「模型层没给诊断」推出「基础设施坏了」。而 28 条 aborted 是兄弟杀的——我们在代码里**知道**原因，却仍然让它们以 died 收场。
- 证伪：给这 28 条补上 `killReason` 后重算 died 数量；若从 145 降到约 117，则 E1 成立。

**E2 精度为 0 的自动修复。** `infraRetry:true` 32 条、`infra:true` 32 条；而 `infra` 只在**最终**结果仍静默时才写入（`round.js:1431` 的条件是 `runRes.infra === true`）。两个数字相等意味着：32 次「重建父会话并重发」没有一次把静默变成诊断。代码注释自己承认 "A rebuilt parent does not fix a broken provider"（`session.js:225-226`），但下一行仍然先重建。
- 证伪：任意一次 infraRetry 之后出现 `diagnosisSource`、`ok`，或 `infra:false` 且无 infraRetry，则 E2 被推翻。

**E3 粒度错配。** attempt 级的 silent 被 round 级消费：`round.js:1604` 要求「所有已派发 attempt 都 `lostToInfrastructure`」才把整轮判为 `interrupted`。一轮两个候选时，一个静默死、一个有补丁，整轮按 `no-gain` 记账——静默污染了任务证据。72/418「有补丁无裁决」里应有一部分来自这里。
- 证伪：统计「本轮 1 个 infra + 1 个非 infra」的轮数；若为 0，则 E3 不成立（我不知道这个数，因为 `infra` 不进 round 级记录）。

**E4 惩罚对象错。** 连续 3 轮 infrastructure 会 `campaign.status{paused}`（`round.js:1651`，`loop.infraPauseAfter` 默认 3）。停的是整个 campaign，而 `models.fallback` 里可能有健康模型从未被试用——418 条记录里 `modelSwitch` 出现 **0 次**，`retried`（小 brief 重试）也是 **0 次**。
- 证伪：是否存在任何一个被 paused 的 campaign 在其 fallback 模型上跑过 attempt。

**E5 可观测性缺失。** `watchdog.checkOne` 已经算出 `idleMs` / `lastSeq`（`watchdog.js:127-132`），但只 `stalls.set()` 进内存（`runtime.js:58`），既不进 ledger 也不进 attempt 记录。回放时无法回答「它死前最后 4 分钟有没有动」——而这正是区分「慢」与「死」的唯一机械证据。
- 证伪：任何一条 attempt 记录里出现 `idleMs` 或 `lastSeq`，则 E5 不成立。

## 4. 「首片零输出 30 秒」能不能当判据

**不能。** 三条理由，都可证伪：

1. **反例就在我们自己的账本里**：47 条 died ≥10s，其中 33 条留下了补丁。若 30s 就杀，这 33 次有产出工作会被提前掐掉。若这 33 条里有任何一条最终通过验证，则规则直接有害。
2. **业界默认值没有这么短**：k8s startup grace 300s；Temporal 心跳节流 30–60s；gRPC 明确建议 keepalive 不要远低于 60s。30s 落在所有默认值之下。
3. **首 token 延迟是模型属性，不是健康属性**：thinking 在最终答案之前（Anthropic）；>32k thinking 已知会撞系统超时与连接上限。

**可以做的降级用法**：把它变成「标签 + 廉价对冲」。
- 标签：记录 `firstSignalMs`（父会话拿到第一个子事件的时间），超过健康样本 p99 就标 `slow-start`，不杀。
- 对冲：若 attempt 还有 ≥ `minFalloverMs`（30s，`config.js:74`）余量，且链上下一个模型可用，就**并行**再发一个候选（是加，不是杀）。
- 这条路的半成品已经在 `session.js:170-173`（`fallbackReserveMs` / `firstSlice`），只差一个「首信号」输入。

## 5. 提案（按 收益/风险 排序）

**P1｜心跳入账**
- 事件日志变化：新增 `attempt.progress{id, round, lastSeq, idleMs, events, firstSignalMs}`（每个 attempt 至少一条终值；可选周期采样）；`attempt.finished` 增 `progress:{lastSeq, idleMs, events, firstSignalMs}`。
- 钉住它的规格：`tests/r1/progress-ledger.mjs`。
- 当前阻止：`watchdog.js:118-143` 只返回内存对象 → `runtime.js:58` 只 `stalls.set`；`reduce.js` 无 `attempt.progress` 分支。
- 净收益：把 145 条 died 从「一个时长分布」变成「可测的死亡分布」，它是 P2/P3/P6 的前置。

**P2｜把 `infra` 拆成两个信号**
- 变化：`failureKind` 增 `silent-no-signal` / `silent-after-progress`；`infra:true` 只在 no-signal 时置；round 级 `interrupted` 只在 no-signal 时触发。
- 规格：`tests/r1/silence-class.mjs`（断言：有过事件的静默死不得让 campaign 暂停）。
- 阻止：`session.js:403,411`；`round.js:84-88,1604`。
- 净收益：按 93/47 双峰，预计 47 条长静默不再触发 campaign 级惩罚。

**P3｜删掉「重建父会话 + 同模型重试」**
- 变化：不再产生 `infraRetry:true`；改为 `attempt.died{retriedSameModel:false, nextModel}`，直接走 fallback 链。
- 规格：`tests/r1/retry-after-silence.mjs`（断言：silent 后不再对同一 model 发起第二次 `#one`）。
- 阻止：`session.js:214-218`。
- 净收益：32 次已证明全败的重试消失；省下的是最贵的一类等待（p50 1.4s，p90 约 350s）。

**P4｜把「谁杀的」从「怎么死的」里拆出来**
- 变化：`attempt.finished.killReason ∈ {sibling, campaign-stop, watchdog, deadline, host-restart}`；`abandoned` 保留为兼容别名。
- 规格：`tests/r1/abort-provenance.mjs`（断言：sibling kill 不出现在 died 分布里）。
- 阻止：`round.js:1481` 写 `{abandoned:true, reason:'solved-by-sibling'}`，`recovery.js:148` 写 `{reason:'host-restart'}`，两套格式。
- 净收益：died 从 145 降到约 117，分母干净后才有资格谈「死亡率」。

**P5｜把「空输出」和「坏协议」分开**
- 变化：`attempt.finished` 增 `produced:{events, textChars, toolCalls}`；`toolCalls>0 && textChars===0` 标 `protocol`。
- 规格：`tests/r1/protocol-vs-silence.mjs`。
- 阻止：`textChars` 已存在（`round.js:1424`）但无人聚合，`events` 未记。
- 净收益：区分「跑了 8 分钟一个字没说」与「一行都没跑」。

**P6｜provider 级冷却（token bucket）替代 campaign 级暂停**
- 变化：新增 `provider.cooling{model, until, silences}`；`campaign.status{paused}` 只在**所有**模型都冷却时发生。
- 规格：`tests/r1/provider-cooldown.mjs`。
- 阻止：`round.js:1651` 直接 pause campaign；无 per-model 失败计数。
- 净收益：一次 provider 抖动不再让某个 campaign 停摆 3 轮。
- 风险：改的是生命周期语义，最后做。

排序：**P1 > P3 > P4 > P2 > P5 > P6**。P1 纯增量只读；P3 是删代码；P4/P5 改字段名会动既有断言面；P2 改判定语义，需先有 P1 的数据；P6 风险最高。

## 6. 我否决的提案

**D1｜用「首片 30s 无输出」直接 kill。** 见 §4：会砍掉 33 条有补丁的长跑，且低于所有业界默认宽限。看着像 liveness probe，实际是 readiness 语义被当成了 liveness。

**D2｜用心跳缺失率算 provider 健康分再据此路由。** `infra` 只有 32 次，按 provider 分桶后每桶个位数——这不是统计，是噪声。而且 AWS 说的「观测到依赖健康才重试」是**正向**观测；健康分是反向推断，等于把 E1 的错误升级成调度策略。

**D3｜给每个 attempt 加重试预算并自动重试到成功。** 验证一次要 41–109s，重试的机会成本是整轮；而 died 里 28 条是兄弟杀的，重试一个「已经被证明不需要」的 attempt 是纯浪费。

**D4｜让 LLM 读子会话日志生成死因。** 回放不可复现（同一条日志两次可能不同分类），与我们 append-only + 机械判据的整体设计冲突。先证明机械判据不够用（P1 的数据会告诉我们），再考虑上模型。

**D5｜把 `died` 改名成 `unknown`。** 不改变任何行为，只让 grep 好看。「未知」已经够多了，缺的是把它拆开。
