# 工作链调度：一轮有出处的研究（2026-11）

> 范围：`dsh-loom` 的**调度层**——`runRound` 的一轮内部（规划/实现/裁决）与跨轮（选任务、停止）。
> 方法与约束：所有数字来自 `~/.dsh/loom/campaigns/*/events.jsonl`（20 个 campaign，含 `loom-triangle`、`loom-tri2`、`loom-self2..14`）与本机账单；所有外部结论附 URL；每条提案都写成一条**当前会失败**的规格测试。
> 不在范围内：`src/exec/*` 的补丁应用、`panel/*` 的 UI、`knowledge/*` 的检索算法（只在受影响时提及）。

## §1 现状：一轮是什么形状，钱和时间花在哪

### 1.1 文字版 DAG（以 `runRound` 为根，括号内为实测）

```
runtime.tick()                        每 20s（config.tickMs），受 switch.json 与 pid-lock 约束
│
├─ selector.pickTask()                纯轮转 index=((round-1)%open.length+open.length)%open.length   ~0ms

│    → node.finished{id,role,round,ok,reused,base,durationMs,sessionId,stopReason,summary}
```

### 1.2 三个最大浪费点（都有 events.jsonl 数字）

**W1 · 规划段每轮全量重跑，占总墙钟 38–39%。**
`loom-tri2` 三轮 recon 分别 510 / 358 / 374s，合计 1242s。而 r2、r3 的任务描述与 r1 **逐字相同**，base 只前进了「上一轮自己晋升的补丁」。`recon-reuse.js` 已存在，但 `planCacheKey()` 把 `base` 放进键里，所以**只要晋升一次（= 每次成功轮）缓存必然 miss**；而 `tri2` 目录下至今没有 `recon-cache.json`（见 1.3 的插件不热重载事实），意味着这三轮 1242s 全是重复劳动。

**W2 · 第二个候选几乎从不改变结果，却贡献 55% 的候选时间与整轮的尾巴。**
六次 attempt：r1a1 636s(score1) / r1a2 **815s**(1) / r2a1 414s(0) / r2a2 **559s**(0) / r3a1 403s(1) / r3a2 422s(0)。a2 合计 1796s = 全部候选时间 3250s 的 **55%**，而 3/3 轮里 a2 都没有带来分数优势（r1 并列 1、r2 并列 0、r3 由 a1 赢）。r1 的两个候选改了**同一组三个文件**（`docs/contracts.md`、`src/runtime/recon-reuse.js`、`src/runtime/round.js`），且三个候选共享同一个 `verifySignature=09d2af8dd222`——盲发候选之间的相关性远高于独立采样假设。
尾巴代价（相对第一个到达者）：r1 **179s**、r2 **145s**、r3 19s。

**W3 · 成本腿完全死亡，`round.finished{status:'budget'}` 是不可达代码。**
对 20 个 campaign 正则抽 `"costUsd":N`：**全部为 0**（同时 `tokens` 非零，如 tri2 r1 = 4570）。链路是 `usageOfSession() → priceUsage(usage, pricing)`，当 pricing 缺 rate 时 `num()→0` 让 usd 恰好是 0 而不是 `null`；于是 `campaignUsage().usd=0`、`spentUsd=0`、`estimatedRoundCost=0`、`exhausted=false` 永远成立——预算闸门只剩 `budget.rounds=12`。
真实花费在另一个文件里：`~/.dsh/.dshw-usage.json` 的 `history["2026-11-07"] = 25.21`（tri2/triangle 跑的那天），**是 campaign `budget.usd=5` 的 5.0 倍**，且该文件有逐事件 `{ts,day,model,cost,tokens}`，是本机唯一的实测账单来源。

> 第 4 个可见浪费（不单列，因为 tri3 规格正在补）：`gateMs` 无字段。tri2 r1 的 109s 裁决段（7.6%）现在无法归因到 holdout / lean / apply 哪一段。

### 1.3 一条会污染所有测量的前置事实（必须先修，否则上面的数字都不能用于 A/B）

`loom-tri2` 的 r2/r3 运行在「r1 刚把 `recon-reuse.js` 晋升进 `src/`」之后，但：(a) `campaigns/loom-tri2/recon-cache.json` 从未生成；(b) 其 `node.finished` 缺 `base`/`reused` 字段，而现码 `src/runtime/round.js:174-187` 的 record **一定**写这两个字段。反证：正在跑的 `loom-chain` 的 `node.finished` 带 `"reused":false,"base":"c02e311a66484e107fd5b2d9eaaf52e315c7c790"`。
结论：**晋升到 loop 自身源码的补丁要等插件重启才生效，而 ledger 当场就把 `chainVersion` 写成新版。** 于是 tri2 后两轮的"新版代码"其实是旧代码，`chainEvidence()` 按 `(chainVersion,taskId)` 聚合时会把两套代码的分数混在一起。

```powershell

Get-Content $d | Select-String '"round.finished"' | ForEach-Object { $_.Line }
# 规划段：node.finished.durationMs 之和；实现段：attempt.finished 最大值；裁决段：wall - 两者
```

## §2 六个方向：已有结论 + 我们的重叠与空白

### 2.1 open-dream-rsi：它的编排层是硬编码常数，我们没有可以抄的调度算法
`https://github.com/patrykorwat/open-dream-rsi`（细读见 `research/odr-study.md`）
- 它自优化的只有三件**任务内**策略：`policy_program` 选树节点、`policy_parameters` 温度/深度随机爬山、`recipe` 解题代码；**编排层（间隔、并发、层级寿命）是常数**，作者明确说 cadence 不由系统决定。
- 事件溯源很干净：8 态/13 边的 ALM、append-only `events.jsonl` + 可重建 `states.json`、`payload_sha256`、`termination_reason` 区分「决策者选择停止」与「运行时移除选项」（`budget_gate|human_stop|agent_stop|tool_error|policy_stop`）。
- **重叠**：我们的 `events.jsonl` + `core/reduce.js` + `replayRounds()` 已经是同一形状，且我们把 L2 回放做成了可执行门（`comparePolicies`），比它更进一步。
- **空白（值得偷的只有一条）**：`termination_reason` 的分类学。我们的 `round.finished.status` 只有 `promoted|no-gain|holdout-failed|budget|exhausted|interrupted`，**把"预算耗尽"与"没增益"混在同一个维度**，回放时无法区分「策略选择停止」和「运行时被砍」。其余（回放门、ALM）我们已实现，不要重复做。

### 2.2 多子代理编排：并行的收益只在「可验证 + 上下文可切分」时成立，我们只满足一半
- Anthropic《How we built our multi-agent research system》`https://www.anthropic.com/engineering/multi-agent-research-system`：orchestrator-worker 在其内部 research eval 上比单 Opus 4 高 90.2%；**token 用量单独解释 BrowseComp 方差 80%**；agent ≈4× chat tokens、多代理 ≈15×；原文「most coding tasks involve fewer truly parallelizable tasks than research」；并行子代理把研究时间最多砍 90%，但前提是子任务之间**不需要共享隐含决策**。
- Cognition《Don't Build Multi-Agents》`https://cognition.ai/blog/dont-build-multi-agents`：原则 1「share context, and share full agent traces」；原则 2「actions carry implicit decisions, and conflicting decisions carry bad results」；并直说 Claude Code 的子代理「usually only tasked with answering a question, not writing code」。
- 我们的 `agentTeams`（spawnTeammate/sendMessage/task board/waitForChange/interrupt）与 `workflowEngine`（fan-out/pipeline 阶段）都具备，但 `runRound` 只用了最弱的一档：**N 个 fresh session 并发写同一棵树的不同 worktree，彼此零共享**。
- 成本侧证据：LLMCompiler `https://arxiv.org/abs/2312.04511`（DAG 并行，延迟最多 3.7×、成本最多 6.7×、精度 +9% vs ReAct）；ReWOO `https://arxiv.org/abs/2305.18323`（计划与观察解耦，约 5× token 效率）。
- **重叠**：并行池 + `maxConcurrent` + worktree 隔离 + `halving` 骨架 + 候选合并裁决都已实现（`self14/parallel-candidates`）。
- **空白**：①「何时**不该**再发第二个候选」——我们无条件发 2 个；②候选之间的**信息传递**（Cognition 原则 1）完全缺失，a1 的 obstacle 笔记只有 a2 在**下一轮**才看得到（`readNotes`）；③没有任何"对冲/早停"语义，第二个候选只能整跑或整不跑。

### 2.3 图/DAG 规划：我们产出的是自由文本，不是可增量修订的结构
- Plan-and-Solve `https://arxiv.org/abs/2305.04091`、Tree of Thoughts `https://arxiv.org/abs/2305.10601`、Graph of Thoughts `https://arxiv.org/abs/2308.09687`（AAAI 2024：顶点=thought、边=依赖，支持聚合/精炼/反馈环）、ADaPT `https://arxiv.org/abs/2311.05772`（按需递归分解）、LLMCompiler `https://arxiv.org/abs/2312.04511`（planner 出 DAG，Task Fetching Unit 并行调度，失败时**局部重规划**而不是整盘重来）、ReWOO `https://arxiv.org/abs/2305.18323`。
- SWE-agent `https://arxiv.org/abs/2405.15793` 与 Aider 的「先定位再改」：计划的第一价值是**定位**（哪些文件/符号），第二才是步骤。
- **重叠**：`chain/spec.js` 有节点/边（`agent|verifier|human|map`）的 DAG，`runPreMapNodes` 已按 DAG 执行 pre-map 段，`chain.templates.js` 有模板。
- **空白**：①recon 的产物是 `RECON_GUIDE` 要求的**纯文本**，worker 拿到的 `plan` 只是一段散文，没有任何「文件 → 改动意图」的映射可被机械校验；②`planCacheKey` 把计划当**整体**缓存（命中/全 miss），没有「继承旧计划 + 追加 Δ」的增量修订路径；③没有局部重规划：base 一动就 100% 重来。

### 2.4 三角经济：best-of-N 在我们的实现里是**负收益**，因为候选高度相关且验证不便宜
- Large Language Monkeys `https://arxiv.org/abs/2407.21787`：重复采样让 coverage 跨四个数量级增长，但**只在候选相互独立、且验证廉价**时转化为性能；coverage 与 precision 缺一不可。
- AlphaCode `https://arxiv.org/abs/2203.07814`：大规模采样 + **按样例过滤 + 聚类**才把 N 变成分数；朴素 N 采样在 N 增大时边际收益迅速递减。
- FrugalGPT `https://arxiv.org/abs/2305.05176`（TMLR 2024）：级联「便宜模型 → 评分器 → 必要时升级」，可「match the best individual LLM with up to 98% cost reduction」——这是**早停**的经济学依据，不是更多采样。
- Successive halving `https://arxiv.org/abs/1502.07943`、Hyperband `https://arxiv.org/abs/1603.06560`、ASHA `https://arxiv.org/abs/1810.05934`：先用便宜预算淘汰，再给幸存者全额预算；我们的 `halving.js` 只有**一级**（`keepRatio=0.5`，且需要 `task.screen.cmd`，实测 `screened:null` 从未启用）。
- speculative decoding `https://arxiv.org/abs/2211.17192` 的可迁移类比：**先跑便宜的草稿，贵的那次只在草稿可能被接受时才付**——对应「对冲派发」，而不是「两个都跑满」。
- **重叠**：`verifier-reuse.js`（同补丁复用裁决）、`tri` 的 `budget-preflight`、`self11/spend-estimate`、`self6/meter-usage`、`cascade` 规格（在飞）都已覆盖一部分。
- **空白**：①候选间的早停/对冲（cascade 是串行等待，反而把墙钟变 sum）；②验证器缓存的键缺 base（见 C4）；③成本从未被测到（见 W3）。

### 2.5 失败与中止：我们的停止条件只有"轮数用完"和"所有任务满分"
- 业界做法：连续 k 轮无增益即停（patience early-stopping），验证器不可达时熔断，预算比质量更紧时降级到最低成本模式。AlphaCode 的采样-过滤-停止、ASHA 的 rung 晋升、以及 ODR 的 `termination_reason` 分类学都是同一件事：**停止必须是一个被记录的事件，而不是一个默认后果**。
- 我们：`plateau.js` 的 `oncePlateau()` 有 `promoted !== true` 的机械判据（好），但**整个 campaign 最多提醒一次**（`state.checkpoints` 里已有 plateau 就不再触发），而且它只 `raiseCheckpoint`，不停止；`runtime.tickCampaign` 只在 `allTasksSolved` 时写 `campaign.status{reason:'all-tasks-solved'}`。
- 实测代价：tri2 r2 花了 958s 换来 score 0，且没有任何机制在 r2 之后叫停。
- **重叠**：`self4/plateau-checkpoint`、`self2/plateau`、`self9/plateau-mutation`、`chaos3/stuck-gate` 已覆盖"提醒"与"变异"。
- **空白**：没有 `flat-streak` 的**自动停止**，也没有把停止写进 `campaign.status{reason}` 的封闭枚举。

### 2.6 与本项目已有研究的交叉
`research/gear-study.md` 的结论对我们最有用的一条是：**promote 的裁决权必须在运行时（`src/runtime/runner.ts:565-620`），算法只能 nominate**——与我们的 `gate.evaluated` 分工一致，说明不要为了"更聪明"把裁决移进 LLM。Gear 的 `manifest + sha256` 密封思路可直接用于 C1/C4 的缓存键（把「被验证的那棵树的指纹」写进键）。

### C1 · `plan-delta`：计划应在 base 小幅前进时被**增量修订**，而不是整段重写

- **改什么**：`src/runtime/recon-reuse.js` 新增 `planDelta(entry, base)` 与 `rememberPlan(..., {base, diffStat})`；`src/runtime/round.js` 的 `runPreMapNodes()`（L165-255）在 `cachedPlan()` miss 后先算 `git diff --stat ${entry.base}..${base}`，若文件数 ≤3 且字节 ≤20KB 且不触及 `tests/`，则**不发模型调用**，直接 `record{reused:true, reusedFrom:entry.base, planDelta:{files,insertions,deletions}}`，计划文本 = 旧计划 + 一段 `Δ since this plan`（来自上一轮 `attempt.report.nextHint` 与 `diffStat.filesChanged`）。`node.finished` 增加 `planDelta` 与 `reusedFrom`。
- **证据**：ReWOO `https://arxiv.org/abs/2305.18323`（计划与观察解耦，约 5× token 效率）；LLMCompiler `https://arxiv.org/abs/2312.04511`（失败/变化时**局部重规划**）；实测：tri2 recon 1242s = campaign 墙钟 38%，r2/r3 的任务描述与 r1 逐字相同，base 只动 1–3 个文件（r1a1 diff 3 文件 ±138 行）。
- **影响的腿**：效率（主）；成本（顺带，少一次 200k token 级规划会话）。
- **期望量化效果**：tri2 r2+r3 省 358+374 = **732s / 3257s ≈ −22%** 墙钟（保守取 r3 单轮 −374s = −11%）；recon 占比 38% → ~13%。
- **机械验证**：`tests/tri4/plan-delta.test.mjs`。构造 fake runtime：r1 无缓存 → 产生 `node.finished{reused:false}`；随后用真实 git 在临时仓库里 commit 一个仅改 1 文件的提交作为新 base；r2 必须产生 `node.finished{reused:true, reusedFrom:<旧 base>, planDelta:{files:1}}` 且 `durationMs===0`，且 dispatcher **没有**收到含 `:plan:` 的 label；把同一个提交改成同时改 5 个文件 → r3 必须 `reused:false`（阈值回退）。当前代码：r2 一定 `reused:false`（键含 base）→ 失败。
- **风险**：陈旧计划导致 worker 按旧文件布局动手 → 用「Δ 段必须列出 base 以来变更的文件」+ 只在 ≤3 文件时启用 + 计划里保留"路径以工作树为准"的指令来兜底。若某轮 no-gain 且 `planDelta` 参与过，下一轮强制全量重规划（自愈）。

### C2 · `hedge`：先发一个候选，到点再发第二个；第一个满分就**杀掉**第二个

- **改什么**：`src/runtime/round.js` 并行池（`workerCount=min(limit,dispatchPlan.length)` 的 `Promise.all+cursor` 段）：改为**分段派发**——a0 立即发；`hedgeAfterMs` 到点（默认 `max(60_000, median(最近 8 次 attemptMs) * 0.5)`）才发 a1。a0 先完成且 `score>=1`（`beatsIncumbent` 已成立）时调 `runtime.watchdog.abort(a1attemptId)`；`round.js:686` 已把 `stopReason==='aborted' && !timedOut` 映射为 `abandoned=stall||'interrupted'`，此处改为写 `'hedged-out'`；`attempt.finished` 增 `hedgedOut:true`，`round.finished` 增 `savedAttemptMs`（= 被杀候选已跑时长）。`config.loopPolicy.candidateMode` 增加第三值 `'hedge'`（与在飞的 `'cascade'|'parallel'` 不冲突，默认仍 `'parallel'`）。
- **证据**：speculative decoding `https://arxiv.org/abs/2211.17192`（便宜的草稿先跑，贵的只在必要时付）；FrugalGPT `https://arxiv.org/abs/2305.05176`（级联早停的 98% 成本降幅）；Cognition `https://cognition.ai/blog/dont-build-multi-agents`（并行的代价是隐含决策冲突）；实测 a2 占 55% 候选时间且 3/3 轮零增益，尾巴 179/145/19s。
- **影响的腿**：效率 + 成本。
- **期望量化效果**：按三轮回放，墙钟 −(179+145+19)=**343s / 3257s ≈ −10.5%**；若 a1 在 a0 完成时平均只跑了 55%，候选 token 省 ≈ a2 的 45% → **总 token −22%~25%**。质量不变（三轮回放中 a2 从未赢）。
- **机械验证**：`tests/tri4/hedge.test.mjs`。假 dispatcher：label 含 `a0` 时 `await sleep(120)` 后写 `solved.txt` 并返回满分报告；label 含 `a1` 时 `await sleep(10000)`（永不完成，需可被 abort）。配置 `candidateMode:'hedge', hedgeAfterMs:50`。断言：①两次 `dispatcher.run` 都发生（a1 确实被启动）；②a1 的调用在 `solved.txt` 出现后被 abort（假 dispatcher 记录到自己收到 abort）；③`attempt.finished` 中存在 `{id:'...a1', hedgedOut:true, score:0, abandoned:'hedged-out'}`；④`round.finished.savedAttemptMs > 0` 且 `skippedCandidates===0`（区分于 cascade 的 `skippedCandidates>0`）。当前代码：a1 会跑满 10s → 断言 ②③④ 全失败。
- **风险**：杀掉候选的窗口内可能杀死本会赢的那个（三样本不足以排除）；abort 是 best-effort（`watchdog.js:52` 注释自认），进程可能多跑几十秒仍计费 → 用 `savedAttemptMs` 实测而非估算。

### C3 · `recon-worktree`：规划节点不该每轮重建一次工作树

- **改什么**：`runPreMapNodes()` 现在每轮 `createWorktree(.../recon-<id>)` 并在 finally 删除。改为持久化一个 `worktrees/<campaign>/_recon` 目录：存在则 `git -C <dir> reset --hard <base>` + `git clean -fdq`，不存在才 `createWorktree`。`node.finished` 增 `worktreeMs`（setup 耗时）与 `worktreeReused`。
- **证据**：本机 Windows 上 `git worktree add` + 检出是分钟级（ledger 里 recon 的 211–510s 包含了它，但**无法分离**——这正是要加 `worktreeMs` 的原因）；Anthropic `https://www.anthropic.com/engineering/multi-agent-research-system`「token 用量解释 80% 方差」提示：非 token 的固定开销是最容易被忽略的那一块。
- **影响的腿**：效率。
- **期望量化效果**：不可先验给出，先量后说；若 `worktreeMs` ≥30s/轮，tri2 省 ≥90s ≈ −3%，并且让 C1 的 200s 级规划增益不被 setup 噪声掩盖。
- **机械验证**：`tests/tri4/recon-worktree.test.mjs`。两轮同 campaign 的规划节点：第一轮 `node.finished.worktreeReused===false && worktreeMs>0`；第二轮 `worktreeReused===true`，且 `git -C <dir> rev-parse HEAD` 等于当轮 base（用真实临时仓库断言），且目录在 campaign 结束后仍存在。当前代码：第二轮 `worktreeReused` 字段不存在 → 失败。
- **风险**：残留脏文件污染计划（用 `clean -fdq` + 断言 HEAD）；并行轮之间共享 `_recon` 需要按 campaign 分目录（已有 `worktrees/<campaign>/` 前缀）。

### C4 · `cost-truth`：把成本从"恒 0"改成"实测"，否则预算闸门永远是死代码

- **改什么**：①`src/runtime/cost.js` 的 `priceUsage(usage, pricing)`：pricing 缺 rate 时回落 `DEFAULT_CONFIG.models.pricing`，**且当 usage 无 token 时返回 `null` 而不是 0**；`usageOfSession()` 返回 `{usd, estimated, source}`。②新增 `ledgerUsd()`：读 `~/.dsh/.dshw-usage.json` 的 `events`，按 round 起止时间戳求 `cost` 之和，写 `round.finished.costUsdMeasured` 与 `costSource:'ledger'|'pricing'|'none'`。③预检改用 `spentUsd = max(state.budget.spentUsd, campaignUsage().usd, campaignUsage().usdMeasured)`。
- **证据**：实测——20 个 campaign 的 `costUsd` 全 0，而 `~/.dsh/.dshw-usage.json` 记录 2026-11-07 花掉 **$25.21**（= 该 campaign `budget.usd=5` 的 5.0 倍）；`priceUsage` 的 `num()→0` 使「未定价」与「真的免费」不可区分（`src/runtime/cost.js:105-114`）；这也是 `estimatedRoundCost()` 恒为 0、`round.finished{status:'budget'}`（`round.js:456`）不可达的根因。参考：Gear 的 `manifest + sha256` 密封（`research/gear-study.md`）——**测量必须锚在账本上，不能锚在模型的自我报告上**。
- **影响的腿**：成本（主）；质量（间接：`gate.minGain` 与预算的权衡需要真实美元）。
- **期望量化效果**：`usdPerPromotion` 从 `null` 变成比如 tri2 = 25.21×2/3 轮 ≈ **$16.8/晋升**（按当日账单摊分，量级正确即可）；预算闸门从"永不触发"变成"第 1 轮就触发（$5 cap）"，逼出下一步的预算策略。
- **机械验证**：`tests/tri4/cost-truth.test.mjs`。①`normalizeConfig({models:{}})` 之后跑一轮，`round.finished.costUsd > 0` 且 `costSource==='pricing'`（当前：0 → 失败）。②给一个 fixture ledger，`events` 覆盖 round 起止区间总 cost=0.37，断言 `costUsdMeasured===0.37`、`costSource==='ledger'`、`usage.estimated===false`。③构造 `spentUsd` 已达 cap 的 state，断言出现 `round.finished{status:'budget'}` 且 `campaign.status{reason:'budget'}`（当前三重前瞻全部为 0，走不到）。
- **风险**：`.dshw-usage.json` 是宿主私有格式（无 schema 承诺）→ 解析失败必须退化为 `costSource:'none'` 而不是崩；ledger 与本轮时间窗重叠会造成重复计数 → 只在 `pricing` 路径缺失时启用。

### C5 · `verifier-key`：验证器缓存的键缺 base 与 tree 指纹，会复用**不属于同一棵树**的裁决

- **改什么**：`src/runtime/verifier-reuse.js:97` 的 `key = sha1(sha1(bytes) + "\n" + keySuffix)`，`keySuffix` 由 `round.js` 传 `cmd+cwd+timeoutMs`。改为 `keySuffix` 追加 `base`（worktree 的 HEAD）与 `testsFingerprint`（`git hash-object` 或 `git status --porcelain` 的 tests/ 摘要）；`inherited()` 把 `stdout/stderr` 里出现的**其他候选 worktree 路径**替换为 `<candidate>`；缓存条目加 `MAX_ENTRIES=64` 按时间裁剪（对齐 `recon-reuse.js` 的 32）。
- **证据**：`verifier-reuse.js:5-8` 的注释自述键应该是"what the verifier actually measures against"——但 base 与树内其它文件同样被测量，注释与实现不符；反例实证：tri2 r3a1 的 `verifySignature=09d2af8dd222` 与 r1a1/r1a2 相同，而三者的 base 各不相同（r1 之后已晋升过 `guard-reuse.js`）。同类问题在 `recon-reuse.js` 已被正确处理（键含 `base`），**两个缓存对"什么算同一份证据"的判断互相矛盾**。
- **影响的腿**：质量（假证据 = 晋升错误代码）；效率（只有键正确，才敢扩大跨轮复用）。
- **期望量化效果**：不能承诺墙钟收益（验证器只占 6–14%）；产出是**消除一类错误晋升**——按 gate 的 `beatsIncumbent` 语义，一次假证据 = 一个被污染的 `chainVersion`，代价是后续所有轮。
- **机械验证**：`tests/tri4/verifier-cache-key.test.mjs`。写入一个 base=A、patch=P 的缓存条目；同一 patch 在 base=B 的工作树上调用 `verifyOnce`，断言 `reused===false` 且 `run` 被调用 1 次（当前：`reused===true` → 失败）；base 仍为 A 时断言 `reused===true`。再加一条：复用后的 `verdict.stderr` 不含 `/worktrees/<campaign>/r1a2` 字样。
- **风险**：键变严格 → 复用率下降、验证器耗时上升；用 `MAX_ENTRIES` 与"同 base 内仍复用"（r1 的 a0/a1 同 base）抵消，实测 tri2 中同 base 的复用仍然存在（r1a1/r1a2 同 base）。

### C6 · `critical-path`：三角补 `gateMs / criticalMs / parallelism`，否则"并行因子"永远是错的

- **改什么**：`src/runtime/round.js` 在 `round.finished` 增 `planMs`（与在飞的 tri3 兼容）、`gateMs`（从 `gate.evaluated` 到 `round.finished` 的墙钟）、`criticalMs = planMs + max(attemptMs) + gateMs`；`src/runtime/triangle.js` 的 `campaignTriangle()` 增 `planMs`（tri3 已要求）、`gateMs`、`criticalMs`、`parallelism = attemptMs / max(attemptMs)`；`parallelFactor` 分母改为 `durationMs - planMs`（现在把 recon 算进分母，实测 1.20 vs 真值 1.51–1.68）。
- **证据**：实测三段对账 tri2 r1 = 510+815+109，而 `round.finished` 只记 `durationMs/attemptMs/verifierMs`，无法分离 109s 的裁决段；`parallelFactor=attemptMs/durationMs` 在 tri2 报 ≈1.20，而 `attemptMs/(durationMs-planMs)` ≈1.63——**现在的指标系统性低估并行度**，会误导"并行没用"的结论。LLMCompiler `https://arxiv.org/abs/2312.04511` 的 3.7× 加速正是按关键路径报的。
- **影响的腿**：效率（度量）；质量（让 C1/C2/C9 的 A/B 有意义）。
- **期望量化效果**：不改运行时行为；产出是把 tri2 的 109s（7.6%）归因、把并行度从错误值 1.20 修正到 1.51–1.68，并把 `criticalMs` 作为后续所有优化提案的唯一记分牌。
- **机械验证**：`tests/tri4/triangle-critical.test.mjs`。构造 rounds：`planMs:80, attemptMs:200（两候选 150/200）, gateMs:20, durationMs:300` → 断言 `criticalMs===300`、`parallelism===1.3333`（1e-4）、`parallelFactor===1.0`（200/(300-80)）。当前：三个字段都不存在 → 失败。（注意不与 tri3 的 `plan-share.test.mjs` 冲突：那边只断言 `planMs/planShare`，本规格只断言新增的三个。）
- **风险**：`gateMs` 的定义边界（holdout 是否算 gate）→ 在规格里钉死为"`gate.evaluated` 事件时刻到 `round.finished` 时刻"，并把 holdout 单列 `holdoutMs`。

### C7 · `token-cap`：预算型 token 停与供应商 token 上限必须解耦，否则每次封顶都翻倍花钱

- **改什么**：`src/dispatch/session.js` 的 `classifyResult()` 现在把 `stopReason==='max-tokens'` 归为 `'tokens'`，而 `Dispatcher.run()` **只对 `{context,tokens}` 换下一个模型**（`modelChain` 回退）。当停因来自我们自己的 `config.session.maxTokens`（`DEFAULT_CONFIG.session.maxTokens=0`，注释自称"Windows 上唯一真正的成本闸门"）时，回退是纯浪费。改为：`classifyResult` 区分 `cap`（本地封顶）与 `tokens`（供应商限制），`failureKind==='capped'` 不回退；`round.js` 的 attempt 记录增 `capped:true`，`round.finished` 增 `cappedAttempts`；同时把 `capped` 排除在 `exhausted` 判定之外（否则整轮会被判成模型耗尽）。
- **证据**：代码事实（`session.js` 的 `MODEL_LIMIT` 正则与 `max-tokens` 分支 + `round.js` 只对 `context` 做缩简报重试）；FrugalGPT `https://arxiv.org/abs/2305.05176` 的反面：任何"升级到更强模型"的动作都应该有明确的触发条件，否则级联就退化成"每次都升级"。
- **影响的腿**：成本。
- **期望量化效果**：一旦设置 `maxTokens`（例如 200k/attempt），当前实现会把一次封顶变成最多 `models.fallback.length` 次额外全量尝试——按 tri2 单个 attempt 平均 540s/约 2.5k tokens 估算，**封顶轮的成本最多 ×(1+fallback 数)**；解耦后为 ×1。
- **机械验证**：`tests/tri4/token-cap.test.mjs`。假 dispatcher 返回 `{stopReason:'max-tokens', timedOut:false}`，配置 `models:{worker:'w1', fallback:['w2']}, session:{maxTokens:200000}` → 断言 `dispatcher.run` **只被调用 1 次**（模型链没有前进），`attempt.finished.failureKind==='capped'`，`capped:true`，且该轮不写 `status:'exhausted'`。当前：第二个模型会被调用 → 失败。
- **风险**：`maxTokens` 的语义在 DSH 侧可能只是"输出上限"而非"总计上限" → 实现前需在 `agentOptions` 上确认参数名；若只是输出上限，则本提案降级为"给 `attempt` 增加 `capped` 标记以便统计"。

### C8 · `flat-streak`：连续 k 轮无晋升就**停止整条战役**，并把原因写进封闭枚举

- **改什么**：`src/runtime/round.js` 轮末维护 `state.flatStreak`（`promoted!==true` 且 `bestScore` 未超过 campaign 历史最高时 +1，否则清零）；`src/runtime/runtime.js` 的 `tickCampaign()` 在 `flatStreak >= config.budget.flatStreakStop`（新默认 3）时写 `campaign.status{status:'converged', reason:'flat-streak', streak, rounds}` 并停止派轮；`src/runtime/plateau.js` 的 `oncePlateau()` 从"整条战役一次"改为"每个 window 轮可再触发一次"（`lastPlateauRound` 字段）。同时给 `round.finished.status` 与 `campaign.status.reason` 建立封闭枚举（`promoted|no-gain|holdout-failed|budget|exhausted|interrupted` / `all-tasks-solved|flat-streak|budget|capped-by-human`）。
- **证据**：ODR 的 `termination_reason` 区分"决策者选择停止"与"运行时移除选项"（`budget_gate|human_stop|agent_stop|tool_error|policy_stop`）——**把预算耗尽记成失败，回放会学出"难任务就放弃"**（`research/odr-study.md`）；ASHA `https://arxiv.org/abs/1810.05934` 的 rung 与 success-halving `https://arxiv.org/abs/1502.07943` 的"不达标就不进下一轮"；实测 tri2 r2 958s / score 0，且此后没有任何机制叫停。
- **影响的腿**：效率（省整轮）+ 质量（`budget.rounds=12` 在 958s/轮下意味着 3.2 小时的沉没成本）。
- **期望量化效果**：若 `flatStreakStop=3`，tri2 会在 r2 后的第二次空转停止——按 958s/轮计，**最多省 1–2 整轮 = 958–1916s（30–59% of campaign）**；且 `campaign.status.reason='flat-streak'` 让回放能区分"没戏"与"没跑完"。
- **机械验证**：`tests/tri4/flat-streak.test.mjs`。假 dispatcher 恒返回 score 0（`beatsIncumbent:false`），`config.budget:{rounds:12, flatStreakStop:2}` → 断言第 2 轮后出现 `campaign.status{status:'converged', reason:'flat-streak', streak:2}`，且**没有第 3 次 `round.started`**；再断言 `state.flatStreak===2` 可被 `reduce` 从事件流重建。当前：会一路跑到 12 轮 → 失败。
- **风险**：过早停掉"先亏后赚"的任务（tri2 r3 正是 r2 之后才晋升）→ 默认 k=3 而不是 2，且"最高分未提高"才计数（分数在涨的轮不算平）；`flatStreakStop` 必须可配置为 0=关闭。

### C9 · `attempt-window`：每次 attempt 的墙钟上限应按历史分位数，而不是固定 20 分钟

- **改什么**：`config.session.attemptTimeoutMs` 现在是常量 20min，而实测 attempt 是 403–815s（p90 ≈ 815s）。改为 `effectiveTimeout = min(config.session.attemptTimeoutMs, max(180_000, p90(最近 8 次 attemptMs) * 1.5))`，在 `round.js` 的 `dispatcher.run({timeoutMs})` 处生效；超时记 `failureKind:'slow'`（不换模型），`round.started` 记 `attemptTimeoutMs` 与 `timeoutBasis:'p90'|'config'`。
- **证据**：ASHA `https://arxiv.org/abs/1810.05934`/successive halving `https://arxiv.org/abs/1502.07943`——预算应随证据收紧；实测 r1a2 815s 是全局 p100，而它零增益（W2），说明长尾候选的信息价值最低。
- **影响的腿**：效率；成本。
- **期望量化效果**：若窗口设为 1.5×p90，tri2 中最长的 815s 候选会在 ~700s 处被截断 → 单轮墙钟 −115s；更重要的是把"卡住的候选"从 20min 上限（1200s）压到 ~700s，**最坏轮墙钟从 1200s 降到 700s（−42%）**。
- **机械验证**：`tests/tri4/attempt-window.test.mjs`。给 8 条历史 attempt（600s×7 + 800s），第 9 轮的 `dispatcher.run` 收到的 `timeoutMs` 必须是 1200s（800×1.5）而不是 20min；且 `round.started.attemptTimeoutMs`/`timeoutBasis==='p90'` 相符；历史为空时回落 config 值且 `timeoutBasis==='config'`。当前：恒 1200000 → 失败。
- **风险**：截断会杀死"高价值慢候选"（tri2 r1a1 636s 是赢家，但没超过窗口）→ 只在 `phase:'explore'` 的候选上放宽到 2×，`exploit` 用 1.5×；超时 attempt 仍参与下一轮 `previousFailure` 提示。

### C10 · `recon-typed`：recon 的产物应该是可机械校验的「文件→意图」表，而不是散文

- **改什么**：`round.js` 的 `RECON_GUIDE` 从"纯文本计划"改为「先输出一个 ```json 的 `[{path, symbol?, intent, evidence}]` 数组（≤8 项），再输出 ≤400 字手记」；`runPreMapNodes()` 解析该 JSON 并用 `fs.existsSync` + `codegraph`/`grep` 校验 `path` 存在（不存在则把该条目标 `stale:true` 传回），校验失败的项数记 `node.finished.planInvalid`；`brief.js` 只把**通过校验**的条目渲染进 `Plan from reconnaissance` 段（超出时按 `evidence` 长度裁剪）。
- **证据**：SWE-agent `https://arxiv.org/abs/2405.15793` 与 Aider 的"先定位再改"（计划的第一价值是定位）；Graph of Thoughts `https://arxiv.org/abs/2308.09687`（顶点=可引用的 thought，边=依赖）；LLMCompiler `https://arxiv.org/abs/2312.04511`（planner 产出结构化 DAG 才能被 Task Fetching Unit 调度）。我们实测：tri2 的两个候选改了**同一组文件**，说明散文计划足以定位，但无法判断"计划是否仍与树一致"。
- **影响的腿**：质量（主）；效率（C1 的"增量修订"需要一个可比对的旧计划结构）。
- **期望量化效果**：不能先验给数字；可量的是 `planInvalid`（幻觉路径数）与"首次 attempt 就 `beatsIncumbent` 的比例"。若 `planInvalid>0`，说明现在每轮都在把不存在的路径喂给 worker。
- **机械验证**：`tests/tri4/recon-typed.test.mjs`。假 dispatcher 返回含 ```json `[{"path":"src/exists.js",...},{"path":"src/ghost.js",...}]` 的计划 → 断言 `node.finished.planInvalid===1`、brief 里只出现 `src/exists.js` 且出现 `ghost` 字样次数为 0、`node.finished.planItems===2`。当前：`RECON_GUIDE` 无 JSON 要求、`planInvalid` 字段不存在 → 失败。
- **风险**：结构化输出让 recon 更容易被截断（1500 字符上限）→ 先只要求 ≤8 项 + 手记可被裁；对老 campaign（散文计划）必须向后兼容（解析失败则整段透传，`planInvalid:null`）。

## §4 明确**不该**做的 3 件事

### 4.1 不该「为并行而并行」（尤其不该把 `candidates` 提到 4）

- **理由**：`maxConcurrent` 是**跨 campaign 共用的进程级闸门**（默认 2），盲目提候选只会把多个 campaign 的一轮都拖成排队；而在同一轮内，候选之间的相关性已经实测很高——r1 的两个候选改了完全相同的三个文件、三个候选共享 `verifySignature=09d2af8dd222`。LLM Monkeys `https://arxiv.org/abs/2407.21787` 的 coverage 增益要求候选**独立**；Anthropic 自己说「most coding tasks involve fewer truly parallelizable tasks than research」；Cognition 的原则 1「share context, and share full agent traces」在我们这里是零共享。
- **反例**：把 N 从 2 提到 4，按现有平均值每个候选 540s、每个 campaign 墙钟不变但 `attemptMs` 翻倍，token 翻倍，而 tri2 的数据显示第二个候选的边际分数贡献是 **0/3 轮**。若真要提高 N，正确的前置是 C5（键正确）+ C10（计划结构化）让候选真正独立，而不是先加钱。

### 4.2 不该「每轮全量重规划」

- **理由**：tri2/ triangle 的 recon 占 38–39% 墙钟，而 r2/r3 的任务 prompt 与 r1 逐字相同、base 只差上一轮自己的补丁。ReWOO `https://arxiv.org/abs/2305.18323` 的核心就是计划与观察解耦复用；LLMCompiler 在失败时做**局部**重规划。全量重规划的代价不是"多花一点 token"，而是**把 40% 的墙钟花在一个答案基本没变的问句上**。
- **反例**：现状本身就是反例——`recon-reuse.js` 已经写好但因为键含 `base` 而永不命中（`tri2` 目录连 `recon-cache.json` 都不存在）。另一种坏做法是"为了避免重规划而永不重规划"：C1 用"Δ 严重则退回全量"来避免这一侧。

### 4.3 不该「用 LLM 判断自己是否收敛 / 该不该停」

- **理由**：①不可复现——`replayRounds()` 与 `comparePolicies()` 只吃已记录的**数字**，一旦停止决策来自 LLM 的自然语言判断，L2 回放就无法重判（这是我们相对 ODR 唯一的结构性优势，别毁掉它）；②ODR 的教训是 `termination_reason` 必须是**封闭枚举**，否则回放会把"运行时被砍"学成"策略选择放弃"（把预算耗尽记成失败 → 学出"难任务就放弃"，见 `research/odr-study.md`）；③`plateau.js` 现有的 `promoted !== true` 机械判据已经在做这件事，缺的只是"停"和"理由枚举"（C8），而不是更聪明的判断器。
- **反例**：让 LLM 读 `events.jsonl` 输出 "converged: true" —— 同一份 ledger 两次运行会给出不同答案，而 `chainEvidence()` 按 `(chainVersion,taskId)` 聚合需要稳定的分母；且它会成为新的成本项（一条 20 轮 ledger 约 50KB，每轮读一次 = 每轮多付一次全量上下文）。
